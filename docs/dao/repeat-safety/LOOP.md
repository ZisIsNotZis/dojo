## 2. 追问、反例、适用条件

一条原话不是一条判断。把它变成能用的一条，要经过三问：

**追问：这句话在说什么取舍？**
两头都要，而且会一起丢：一头是「把每次请求分别记下来、事后分得清」，另一头是「重放不改动已完成的状态」。
只留第一头，重放让已完成的工作重新变成待办；只留第二头，两次不同的请求在账本里长得一样。

**反例：有没有它不成立的地方？** 有两条，都写进 `off`，而且**都真的改变了动作**（否则就是装饰）：

| 失效条件 | 轴 | 动作变成什么 |
|---|---|---|
| 这笔操作没有可比的状态（纯追加、每调一次都产生新对象） | `has_state` | 不按请求判重，只按效果判，并把「这里没有状态可比」印出来 |
| 判重的人就是写出这次请求的那个作者 | `judge` | 判重照旧，但换一个独立的一方复核，并把「谁复核的」写进回执 |

**适用条件：什么时候用它。** 情境写全了三件（谁、何时、约束），并落了两个域：工具与流程、重试与幂等。

## 6. 出处核对：`source` 从装饰变成被读的字段

这一片加了一条门（`scripts/dao_life.py` 的 `check_sources`），它问两个问题，分开答：

- **引语**：把空白压平后，引语必须逐字出现在 `source.path` 的文件里，并且 `source.ref` 里写的行号
  必须落在引语所占的**最紧**的区间内。行号指向别处就是一张旧地图，读者照着走会走错段落，所以与「找不到」同罪。
- **提交**：写下的提交必须在本仓解析得出。解析不出来就记成 `unresolved` 并**印出来**，不并进 pass：
  引语找到了、版本没核到，这是两件事，一句话说不清就会说成一句假话。所以判定有三个词：`pass` / `unchecked` / `fail`。

它一上线就在真库上抓到两处真错，都已修好：

| 库里的行 | 错在哪 | 修法 |
|---|---|---|
| `ep-2026-10-18-pref` | 引语把第 5、6 两行**拼成了一句**，文件里它们是两条分开的要点；照它去找，一个字也找不到 | 只引第 5 行；第 6 行单独成 `ep-2026-10-18-pref-b` |
| `ep-2026-10-23-detach` | `ref` 指第 104 行，那句话在第 **111** 行 | 改成第 111 行 |

另外 20 条 episode 写的提交号（`41d925a`、`8ed7cb5`、`4897660` …）在本仓**一个都解析不出来**：
历史被重建过，那些对象不在了。这不是我这一片造成的，但它是这些记录一直没被读过的证据。
处理方式写进每条 episode 的 `citation_note`：改指本仓现存最早包含该引语的提交（`1af799f`），
并写明原来写的是什么、为什么不再保留。**没有假装它们被核过。**

## 7. 这条链还证明不了什么

- **它不是「他的看法」。** 六件里五件是系统补的，所以它是「他这样做的假设」。要变成他的话，只有一条路：
  他后来自己说一句确认或推翻，逐字落进事件层并带回执。现在晋升 0 条。
- **三处落地都是同一只手量的。** `map.json` 里那条连接标着「待确认（三处都是同一只手量的，不是独立复核）」。
  一处改错又改对（决定 B），说明这只手会错；它不能自己给自己发独立复核的奖。
- **决定 C 只是边界，不是证据。** 它证明判据知道自己不该用在哪，不证明判据在边界之内都对。
- **`check_sources` 把空白压平**，所以「把上一段结尾和下一段开头拼成一句」这种引语会被判成命中。
  这是为了让跨行折行的引语能过而付的代价；行号是让读者自己看出接缝的那条线。这条限制写在
  `tests/test_source_citations.py` 里，不是留给人以后重新发现。
- 只在这一台机器、这一个 Python 上跑过。读数里没有秒数：同一套在不同负载下差得太多，它不是证据。

## 9. 复核人用正常 CLI 找到的两个反例（都成立，已修）

复核不是再读一遍代码，是拿普通命令去用。两处都落在这条判断管辖的重试/核对路径上，两处都是我的错。

### 反例一：无组别来源的重放报错

两个会话各给一条**没注明组别**的材料，然后把第二条原样再发一次：

```sh
python3 -m dojo add --id c1 --kind abstract_idea --statement '句子' \
  --source-json '{"id":"src-a","type":"unknown","claim":"甲先说的","verification":"unknown"}' --session s1
python3 -m dojo attach-source c1 \
  --source-json '{"id":"src-b","type":"unknown","claim":"乙再说的","verification":"unknown"}' --session s2
python3 -m dojo attach-source c1 \
  --source-json '{"id":"src-b","type":"unknown","claim":"乙再说的","verification":"unknown"}' --session s2
```

| | 上一版（`67daf16`） | 现在 |
|---|---|---|
| 重放那一行的退出码 | **2**，`error: source ID already exists: src-b` | **0** |
| 账本 | 不动 | 不动 |

原因：我拿 `independence()` 去问「这一条来源算不算新 provenance」，而它算的是**整张卡**；
我把候选来源接进 `state` 又补一条合成事件，于是同一条被数了两遍，读出一组并不存在的组别，
再往下走就撞上 `_source_ids_available` 的重名检查。判据问错了层级：这里要问的是**一条来源**。
现在是一个谓词，三种「同一份 provenance」都写在里面（同一来源对象 / 同一具名组 / 无组别但同一会话交的），
`"unknown"` 按「没写组名」处理而不是当成组名。

### 反例二：提交存在，但那份文件在那个修订上还不存在

把一条正确引语的提交号换成本仓**确实存在**、但那时还没有那份文件的提交，核对仍说 `pass`。
`git cat-file -e <sha>^{commit}` 只证明对象在，不证明路径在。一条引语不能拿一个从未包含它的修订去核对。
现在提交要过两关：是提交，**并且**那个修订上有这份文件。状态因此多一个词 `missing-path`，判 `fail`；
「提交不在库里」仍是 `unchecked`——三个词对应三件事，不合并。

## 10. 第二轮复核又找到的边界（都成立，已修）

### 边界一：引语要按**所指的那个版本**核对，不是工作树

同一个路径在两个提交里都有，但那句话是第二次才写进去的。把引语指回第一次：上一版判 `pass`，
而顺着引用去那个版本读的人找不到这句话——引用是可复核的承诺，承诺的东西不在就不算核过。

现在引语与行号都取 `git show <commit>:<path>` 的内容来比。没有历史可问时（冻结解出的树）用工作树，
但状态写 `checked_at: working-tree`、判定写 `unchecked`——**不假装问过那个版本**。
`--check` 那一行因此会印「按所指版本核对 N 条」。

### 边界二：无组别的来源要保留会话判据，具名的新分组仍要入账

```sh
# s1 建一条无组别来源；s2 加一条同样无组别的；然后 s1 再加一条无组别的
```

| | 公开版（`09eca15`） | 上一版（`a80e5c0`） | 现在 |
|---|---|---|---|
| s1 的第三条 | 账本不动 | **多写一条** | 账本不动 |
| s1 带一个**新具名分组** | 被会话判据挡住（缺陷） | 入账 | **入账** |
| 原有无组别来源的会话归属 | 保留 | 保留 | 保留 |

上一版把会话判据整个删了。那条判据**太宽**，但不错：无组别来源没有自己的键，交它的会话就是它唯一的身份。
现在只对无组别来源保留会话判据；具名分组按组判——两个问题各自问自己的键。

## 11. 第三轮复核：读的是哪个版本，读的是哪一处（都已修）

复核人拿一句带出处的话去查，回来两个读数。两个都是真的。

### 缺陷一：一句话出现两次，引了第二处的准确行号，却被判成错行

同一个文件里同一句话在第 3 行和第 5 行各出现一次。`ref` 写「第 5 行」——**准确**。
上一版只拿 `ref` 跟**第一处**比，于是这一条判 `stale-ref`、`fail`。

这不是「门太松」，是门把一个对的行号当成了错的地图。行号存在的意义正是**指定哪一处**，
所以现在先找出全部出现位置，再用 `ref` 选。没有写行号时才取最紧的一处。

| | 上一版 | 现在 |
|---|---|---|
| 引第 5 行（第二处） | `stale-ref`，`fail` | `found`，`pass`，`lines [5,5]` |
| 引第 3 行（第一处） | `pass` | `pass` |
| 引第 2 行（哪处都不是） | `fail` | 仍 `fail`，且行里给出真实位置 `3–3、5–5` |
| 会出现几次 | 不说 | `occurrences` 列全部位置，`occurrence_note` 说明按 `ref` 取了哪一处 |

真实库里就有一条这样的引语：`repeat-safety` 的那句原话在 `docs/proposal-knowledge-network.md`
第 111 行和第 307 行各有一份。现在回执里写着这件事，读者能自己去看另一处。

### 缺陷二：旧修订的文件读不出来时，工具拿工作树顶替，还说 `pass`

两种形状，同一种谎：

* 所指的提交在库里、但那个修订上**没有这份文件**，而工作树里有。`git show` 拿不到东西，
  于是回退去读工作树。回执那一行写着 `found`——引语是在**今天的文件**里找到的，不是在引用的版本上。
* 所指版本里的文件**不是 UTF-8**（一个 Latin-1 重音字符就够）。`git show` 成功了，解码失败，
  而失败和「没有这个 blob」落进了同一个分支 → 回退读工作树 → `pass`。
  **最弱的证据拿到了最强的结论**，而且只要在旧版本里写一个带重音的词就能买到。

现在只有在**根本问不到版本**的时候才读工作树：没有 `.git`（冻结解出的树）、`git=False`、没写 commit、
或 `synthetic`（那批语料本来就写在这里）。其余情况下版本问不到就如实说问不到：

| 情形 | 上一版 | 现在 |
|---|---|---|
| 所指修订上没这份文件 | `quote: found`（读的是工作树），`commit_state: missing-path`，`fail` | `quote: unchecked-at-revision`，`checked_at: no-revision`，`fail` |
| 所指版本不是 UTF-8 | **`pass`** | `quote: unreadable-at-revision`，`checked_at: no-revision`，`fail`，并写出为什么 |
| 提交不在本仓 | `found`（读工作树）+ `unchecked` | `unchecked-at-revision` + `unchecked`（不当作错，只是没问到） |
| 冻结树（无 `.git`） | `working-tree` + `unchecked` | 不变 |
| `synthetic` | `working-tree`，不需 commit | 不变 |

回执的读数行也分开了：「不可解析 N 条」是提交不在库里，「引语没能在这个版本上核对 M 条」是版本读不出来；
两者不再合并成一个数。读数版本号升到 `sources-v3`（其余三项读数没变，所以 `BENCH_VERSION` 不动）。

### 这一轮的红臂

`tests/test_recheck_occurrences.py`，15 项。在 `9f76a2b` 的**真克隆**里 `checkout` 后跑：
`Ran 15 / FAILED (failures=5, errors=9)`，按具体测试算是 **11 项红、4 项绿**
（两个带子测试的会把同一项报两遍）。

我第一遍把这条量错了：那次是把 `9f76a2b` 用 `git archive` 解到无 `.git` 的目录里跑，多了两个
「无历史」skip、少了三个会真去查提交的用例，于是记成 `8 红 6 错`。红臂必须在**有历史**的同版本树上量，
否则量的是另一个问题。

红的 7 项是这两个缺陷本身：重复句按 `ref` 取、修订缺文件时借用工作树、非 UTF-8 判 `pass`、
提交不在本仓时去读工作树、读数行不分计数、整库不变量「`pass` 不能建立在工作树读数上」、
以及回执还停在 `sources-v2`。错的 4 项是三个新字段（`occurrences`、`occurrence_note`、
`unchecked_at_revision`）在那棵树上还不存在。现在 15 项全绿。

```sh
python3 -B -m unittest tests.test_recheck_occurrences
```

另有四项在两种树上都绿，是防过度收紧的门：第一处仍 `pass`、哪处都不是仍 `stale-ref`、
冻结树仍读工作树且判 `unchecked`、能解析且含该文件的提交仍 `pass`。

### 还证明不了什么

* **空白压平仍在**。把上一段结尾和下一段开头拼成一句，仍会被判命中；行号是唯一能暴露接缝的东西。
  这一轮没有把门变严，只把「读的是哪个版本、哪一处」这两件事说准。
* **非 UTF-8 的旧版本现在判 `fail`**，不是 `unchecked`。这是有意的：这条引语在一个有人能读的版本上
  也许确实成立，但**用这个修订核对不了**，而记录声称它就是出处。若将来真有这种引语，办法是把 `ref`
  指向一个文本可读的版本，而不是让门悄悄换一个版本去读。
* 三处落地仍是同一只手量的，`map.json` 标着「待确认（不是独立复核）」。

## 12. 第三轮独立复核找到的两处旧缺口（都不是本轮引入，但都是真的）

复核人 PASS 了 `0aeef3b`，同时报了两处。两处在上一版就存在，不是这次改坏的；我不把它们当「超出范围」
推掉，因为它们和这一轮在问的是同一个问题：**记录里的东西到底钉住了什么**。

### 缺口一：`commit` 可以是会动的名字

`HEAD`、分支名、`HEAD~1`、轻量 tag 都能被 `git` 解析。上一版把「能解析」当成「钉在了某个版本上」，
于是判 `resolved`、按解析到今天的位置去读引语。复核人把一个分支 reset 回旧提交、**记录一个字没改**，
读数从 `fail / absent` 变成 `pass / found`。

一条引语是写给几年后的读者的承诺；会动的名字守不住这个承诺。现在只有**对象哈希**（缩写或全长十六进制）
算 `resolved`；其余一律 `moving-name`：判 `fail`，`checked_at: no-revision`，行里直接说「请写对象哈希」。

真库不受影响：20 条 episode 写的都是十六进制哈希。但规则变了之后，「commit 在本仓解析得出」才真等于
「在那个修订上」。

**光是「长得像哈希」还不够。** 第一版只查字符串是不是十六进制，漏了一种情况：`git tag 1af799f` 能建一个
**名字是十六进制**的标签，而 git 遇到这种名字优先按名字解析——实测同一串字符解到了另一个提交。
记录于是可以写一个版本、读另一个版本的内容。现在两问都要过：

1. 这个名字**不能同时是一个 ref**（`refs/tags/`、`refs/heads/`、`refs/remotes/`）——标签能用 `-f` 重指，
   就算今天指向对的对象，它也不是承诺；
2. 解析出来的对象 id **必须以这个名字开头**。对真正的对象 id 这是恒真，对缩写这是定义，
   对其他解析路径这就会失败。

实测：一个指向正确提交、名字是完整哈希的标签仍被拒（`names_object=False`）；同一提交的直接哈希则通过。

### 缺口二：`ref` 里别的数字能顶替错掉的行号

旧解析把 ref 里**每一个** `第 N` 都当行号。于是 `第 29 行，见第 2 节` 会通过：3 不在引语范围里，
2 在，而门只问「有没有某个数字落进去」。真库已经可达：`person-dojo/ep-2026-10-23-detach` 的 ref 是
`第 111 行；§10 第 2 条（第 272 行）`，三个数字。**今天它恰好判在 `[111,111]`，是运气，不是构造。**

现在只认 `第 N 行` 和 `N–M 行`；`第 2 条`、`§10` 不再算行号。区间**保持为区间**：

```
引语占 [3,3]，ref 是 第 1–5000 行  →  3 ≤ 5000 且 1 ≤ 3  →  相交，pass
```

要问的只有一件事：引语落在不在这个范围里。把 `第 1–5000 行` 展开成五千个整数不换来任何准确性，
只把一个可信的笔误变成一次分配。宽区间是记录写得粗，不是门写得准；这一轮不限制宽度。

| ref | 上一版 | 现在 |
|---|---|---|
| `第 3 行`（对） | `pass` | `pass` |
| `第 29 行，见第 3 节` | **`pass`**（3 顶了 29） | `fail`，`stale-ref`，位置给 `3–3` |
| `第 4 行；§3 第 3 条` | **`pass`** | `fail` |
| `第 111 行；§10 第 2 条（第 272 行）` | `pass`（靠运气） | `pass`（只把 111 与 272 当行号） |
| `第 29–30 行`（句子在 30） | `stale-ref` | `pass` |
| `第 1–5000 行`（句子在 3） | `stale-ref` | `pass`（相交即算，不展开） |

### 这两处也在交付检查里

`tests/test_moving_names_and_refs.py`，20 项：十六进制与缩写哈希仍 `resolved`、`HEAD`/分支/`HEAD~1` 判
`moving-name`、**名字是哈希的标签也拒**（轻量与 annotated 两种，且指向正确对象也拒）、
**分支移动不能翻转已钉住的记录**、真库无一会动名字、真库每条 ref 都解得出行号、
宽区间是一次比较而不是展开，以及三条防过度收紧的门（对的行号仍 `pass`、区间含引语仍 `pass`、
ref 无行号时取最紧一处）。

```sh
python3 -B -m unittest tests.test_moving_names_and_refs
```

红臂：两个新套件合起来 35 项，在 `9f76a2b` 的**真克隆**里 `Ran 35 / FAILED (failures=15, errors=53)`，

红的是这两处缺口与两处旧缺陷；绿的全是「不能收紧」的对照组（真哈希仍 `resolved`、

这一点写在这里，免得下一次有人把它当成环境问题。

### 还留着的两件事（复核人报的，我判定不改）

* **区间 ref 只读第一个数字**已经不存在：现在是整段区间。但反过来，区间会放宽而不是收紧：
  `第 1–100 行` 只要引语在范围内就 `pass`。宽区间是记录写得粗，不是门写得准。我没有限制宽度。
* **冻结树模式下 `path` 可以指到库外**（`../../x.md`、绝对路径）。裁定时会读取人指定的文件。
  这是「冻结树只能读工作树」的同一个限度，不是新缺陷；写在这里，不让下一个人重新发现。
* 「空白压平」仍在（见上一节的「还证明不了什么」）：复核人也验到了。
