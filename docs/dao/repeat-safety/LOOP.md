## 1. 从一段原始叙述开始

事情的起点是一句原话，不是我的概括。他在 `docs/proposal-knowledge-network.md` 第 111 行写下：

> "it's not user confirm, user is already detached, he's not responsible for challenging,
> your underlying network is. He CAN challenge later, e.g. 'did you do simulation?',
> but not responsible for reminding that."

这一行分成三件事，后来每一步都靠它们分开：

| 是什么 | 内容 | 谁给的 |
|---|---|---|
| **人类经验** | 他已经抽身；检查归网络；他保留「随时来问」的权利，但不负责提醒 | 他的原话，一字未改 |
| **模型/管理者的推断** | 所以「持续检查该由系统接走」；所以重放也该由系统自己判、不回头问人 | 我写的，标 `系统补` |
| **实际证据** | 那三处决定改前改后的读数 | 命令跑出来的，见 `observations.json` |

同一天的记录里还有一个**已观察到的动作**：他把 M1.5 的用户检查点从「还没」翻成「确认」，
不是自己去当检查者，而是让系统把那一局跑完再回来推翻或确认。这是这条经历里唯一的动作记录，
也是它能成为「案例」而不只是「引语」的原因（`独立来源` 那一栏只数有动作的案例）。

## 2. 追问、反例、适用条件

一条原话不是一条判断。把它变成能用的一条，要经过三问：

**追问：这句话在说什么取舍？**
两头都要，而且会一起丢：一头是「把每次请求分别记下来、事后分得清」，另一头是「重放不改动已完成的状态」。
只留第一头，重放让已完成的工作重新变成待办；只留第二头，两次不同的请求在账本里长得一样。

**反例：有没有它不成立的地方？** 有两条，都写进 `off`，而且**都真的改变了动作**（否则就是装饰）：

| 失效条件 | 轴 | 动作变成什么 |
|---|---|---|
| 这笔操作没有可比的状态（纯追加、每调一次都产生新对象） | `has_state` | 不按请求判重，只按效果判，并把「这里没有状态可比」印出来 |
| 判重的人就是写出这次请求的那个作者 | `judge` | 判重照旧，但换一个独立的一方复核，并把「谁复核的」写进回执 |

**适用条件：什么时候用它。** 情境写全了三件（谁、何时、约束），并落了两个域：工具与流程、重试与幂等。

## 4. 在另一项实际决定里验证它有没有改变行动

这条判断被拿到三处决定上用，三处都是**先读改前、再读改后**，读数由命令现场重算：

### 决定 A：一个被截断的响应该不该重发

`dojo/live.py` 把「正文比 `Content-Length` 短」归成模型格式错误，`dojo/discuss.py` 因此自动重试两次。
按这条判断去问「我有证据说第一次没生效吗」——没有。于是不重试，并如实说传输断了。

| | 改前 | 改后 |
|---|---|---|
| 一个用户回合发给服务端的请求数 | **3** | **1** |
| 客户端给这种失败的种类 | `not_json` | `incomplete_response` |
| 用户被告知模型格式不合法 | 是 | **否** |

### 决定 B：`attach-source` 该按会话判重，还是按来源判重

**这一处是真的缺陷，也是这条判断最有力的一次。** `attach_source` 用「这个会话是否已经贡献过」当判据：

```sh
python3 -m dojo add --id c1 --kind abstract_idea --statement '句子' \
  --source-json '{"id":"src-a", ...,"independence_group":"g-a"}' --session s1
python3 -m dojo attach-source c1 \
  --source-json '{"id":"src-b", ...,"independence_group":"g-b"}' --session s1
python3 -m dojo show c1     # 改前：只有 src-a；rc 0，没有事件，没有错误
```

| | 改前（`09eca15`） | 改后 |
|---|---|---|
| 退出码 | 0（看起来成功） | 0 |
| 写了什么事件 | **没有** | `attach_source` |
| 卡上的来源 | `['src-a']` | `['src-a', 'src-b']` |
| 第二个来源 | **被静默丢掉** | 收录 |

改前的代码拿一个**相邻的东西**（会话）当判据，而写这条判断的人自己也先写错过一版：第一版改成
「来源对象是否相同」，还被已发布的契约挡了回来（见下）。判据最后落在仓库已有的 `independence()` 上——
它本来就在回答「这个来源算不算一条新 provenance」，不需要第四套尺子。

### 决定 C：`distill` 判「重复」时该看什么（判断说它自己不该用在这里）

`pass_locate` 用 `content_key` 判重复，而 `content_key` **故意不比较 `sources`**。按这条判断的失效条件，
这里没有「状态」可比：同一句话配第二个来源，是来源变多了，不是有人又做了一遍。所以那里按效果判是对的。
这一格是「判断说出它不该用在哪」，比多一个正例弱，如实写明。

## 6. 出处核对：`source` 从装饰变成被读的字段

这一片加了一条门（`scripts/dao_life.py` 的 `check_sources`），它问两个问题，分开答：

- **引语**：把空白压平后，引语必须逐字出现在 `source.path` 的文件里，并且 `source.ref` 里写的行号
  必须落在引语所占的**最紧**的区间内。行号指向别处就是一张旧地图，读者照着走会走错段落，所以与「找不到」同罪。
- **提交**：写下的提交必须在本仓解析得出。解析不出来就记成 `unresolved` 并**印出来**，不并进 pass：
  引语找到了、版本没核到，这是两件事，一句话说不清就会说成一句假话。所以判定有三个词：`pass` / `unchecked` / `fail`。

它一上线就在真库上抓到两处真错，都已修好：

| 库里的行 | 错在哪 | 修法 |
|---|---|---|
| `ep-2026-10-18-pref` | 引语把第 5、6 两行**拼成了一句**，文件里它们是两条分开的要点；照它去找，一个字也找不到 | 只引第 5 行；第 6 行单独成 `ep-2026-10-18-pref-b` |
| `ep-2026-10-23-detach` | `ref` 指第 104 行，那句话在第 **111** 行 | 改成第 111 行 |

另外 20 条 episode 写的提交号（`41d925a`、`8ed7cb5`、`4897660` …）在本仓**一个都解析不出来**：
历史被重建过，那些对象不在了。这不是我这一片造成的，但它是这些记录一直没被读过的证据。
处理方式写进每条 episode 的 `citation_note`：改指本仓现存最早包含该引语的提交（`1af799f`），
并写明原来写的是什么、为什么不再保留。**没有假装它们被核过。**

## 7. 这条链还证明不了什么

- **它不是「他的看法」。** 六件里五件是系统补的，所以它是「他这样做的假设」。要变成他的话，只有一条路：
  他后来自己说一句确认或推翻，逐字落进事件层并带回执。现在晋升 0 条。
- **三处落地都是同一只手量的。** `map.json` 里那条连接标着「待确认（三处都是同一只手量的，不是独立复核）」。
  一处改错又改对（决定 B），说明这只手会错；它不能自己给自己发独立复核的奖。
- **决定 C 只是边界，不是证据。** 它证明判据知道自己不该用在哪，不证明判据在边界之内都对。
- **`check_sources` 把空白压平**，所以「把上一段结尾和下一段开头拼成一句」这种引语会被判成命中。
  这是为了让跨行折行的引语能过而付的代价；行号是让读者自己看出接缝的那条线。这条限制写在
  `tests/test_source_citations.py` 里，不是留给人以后重新发现。
- 只在这一台机器、这一个 Python 上跑过。读数里没有秒数：同一套在不同负载下差得太多，它不是证据。

## 9. 复核人用正常 CLI 找到的两个反例（都成立，已修）

复核不是再读一遍代码，是拿普通命令去用。两处都落在这条判断管辖的重试/核对路径上，两处都是我的错。

### 反例一：无组别来源的重放报错

两个会话各给一条**没注明组别**的材料，然后把第二条原样再发一次：

```sh
python3 -m dojo add --id c1 --kind abstract_idea --statement '句子' \
  --source-json '{"id":"src-a","type":"unknown","claim":"甲先说的","verification":"unknown"}' --session s1
python3 -m dojo attach-source c1 \
  --source-json '{"id":"src-b","type":"unknown","claim":"乙再说的","verification":"unknown"}' --session s2
python3 -m dojo attach-source c1 \
  --source-json '{"id":"src-b","type":"unknown","claim":"乙再说的","verification":"unknown"}' --session s2
```

| | 上一版（`fc65d5e`） | 现在 |
|---|---|---|
| 重放那一行的退出码 | **2**，`error: source ID already exists: src-b` | **0** |
| 账本 | 不动 | 不动 |

原因：我拿 `independence()` 去问「这一条来源算不算新 provenance」，而它算的是**整张卡**；
我把候选来源接进 `state` 又补一条合成事件，于是同一条被数了两遍，读出一组并不存在的组别，
再往下走就撞上 `_source_ids_available` 的重名检查。判据问错了层级：这里要问的是**一条来源**。
现在是一个谓词，三种「同一份 provenance」都写在里面（同一来源对象 / 同一具名组 / 无组别但同一会话交的），
`"unknown"` 按「没写组名」处理而不是当成组名。

### 反例二：提交存在，但那份文件在那个修订上还不存在

把一条正确引语的提交号换成本仓**确实存在**、但那时还没有那份文件的提交，核对仍说 `pass`。
`git cat-file -e <sha>^{commit}` 只证明对象在，不证明路径在。一条引语不能拿一个从未包含它的修订去核对。
现在提交要过两关：是提交，**并且**那个修订上有这份文件。状态因此多一个词 `missing-path`，判 `fail`；
「提交不在库里」仍是 `unchecked`——三个词对应三件事，不合并。

### 这两个反例现在在交付检查里

`tests/test_recheck_counterexamples.py`，6 项：其中 2 项在上一版 `fc65d5e` 上红、现在绿，
另 4 项是防过度收紧的回归门（第二个会话仍然新增 provenance、同一具名组仍是 no-op、
能解析且含文件的提交仍 `pass`、不存在的提交仍 `unchecked`），在两种树上都绿。
第一项用 CLI 跑，走的正是复核人用的那条路；第二项在真实的两个提交的临时仓里跑。

```sh

```

## 10. 第二轮复核又找到的边界（都成立，已修）

### 边界一：引语要按**所指的那个版本**核对，不是工作树

同一个路径在两个提交里都有，但那句话是第二次才写进去的。把引语指回第一次：上一版判 `pass`，
而顺着引用去那个版本读的人找不到这句话——引用是可复核的承诺，承诺的东西不在就不算核过。

现在引语与行号都取 `git show <commit>:<path>` 的内容来比。没有历史可问时（冻结解出的树）用工作树，
但状态写 `checked_at: working-tree`、判定写 `unchecked`——**不假装问过那个版本**。
`--check` 那一行因此会印「按所指版本核对 N 条」。

### 边界二：无组别的来源要保留会话判据，具名的新分组仍要入账

```sh
# s1 建一条无组别来源；s2 加一条同样无组别的；然后 s1 再加一条无组别的
```

| | 公开版（`09eca15`） | 上一版（`abcf0df`） | 现在 |
|---|---|---|---|
| s1 的第三条 | 账本不动 | **多写一条** | 账本不动 |
| s1 带一个**新具名分组** | 被会话判据挡住（缺陷） | 入账 | **入账** |
| 原有无组别来源的会话归属 | 保留 | 保留 | 保留 |

上一版把会话判据整个删了。那条判据**太宽**，但不错：无组别来源没有自己的键，交它的会话就是它唯一的身份。
现在只对无组别来源保留会话判据；具名分组按组判——两个问题各自问自己的键。

### 这两个边界也在交付检查里
