# 四条可迁移 seed 候选 v1（模拟材料）

> **历史材料（v1 editor-bridge 评价）。**本页的四条 seed 不再由当前 demo 使用；当前 seed 见 [seed-pack-v2.md](seed-pack-v2.md)。

> **数据性质：**这是写好的 POC 模拟语料，不是观察到的用户研究、已验证实践或真实证据。来源案例是“代码生成器改变输出格式，旧/新插件消费生成物”；它与另一文件中的 editor-bridge 重试目标是不同案例。两者在组件兼容边界上有宽泛可迁移关系，但没有复用目标的确切答案或措辞。
>
> 正向 C 条件只可向答题模型传递明确指定的记录摘录，不传本说明、完整主持人笔记或评分备注。本演示包的 C-selected 集合为 S01–S04。无关材料只用于 `C-irrelevant` 负控制，不混入正向 seed。

## 来源案例

虚构构建工具“Forge”把生成文件格式从格式 A 改为格式 B；文件会被旧、新版本插件读取。已知只有 Forge 自身单元测试全绿，未提供旧/新消费端兼容矩阵、工单或生产资料。此源案例是独立准备的模拟输入，不是目标测试答案。

## S01 — 抽象想法：交界不等于组件各自正确

- **主张：**兼容性问题可能出现在两个组件交接的约定处；各组件分别通过自己的测试，并不自动说明双方对同一产物的理解一致。
- **类型/来源：**`abstract_idea` / `abstract_reasoning`；作者按虚构源案例写成，没有经验支持。
- **前提/边界：**两边确有共享格式或协议；若某消费端已不在支持范围，此边界可能没有决策价值。
- **核验：**`not_evidence`。这是一条值得讨论的抽象区分，不是兼容失败报告。

## S02 — 条件路线甲：可低成本覆盖受支持版本时做交界检查

- **主张：**若旧、新消费端版本都仍受支持，且可低成本构造同一生成物的检查，比较双方如何读取这份产物，可能比只跑生成器自身测试更能暴露交界分歧。
- **类型/来源：**`application` / `abstract_reasoning`；从模拟源案例推演。
- **条件：**支持范围已确认、两端检查可信且成本可接受。
- **核验：**`not_evidence`。这里没有真实兼容矩阵或测试结果。

## S03 — 条件路线乙：测试边界无法构造时不声称已覆盖

- **主张：**若某些消费端版本无法复现，不能把单一路径的绿灯说成兼容性已覆盖；可以明确记录未知、先确认哪些版本仍在支持范围，或让负责者决定是否接受未验证的边界，而不是假装已有完整证据。
- **类型/来源：**`application` / `abstract_reasoning`；与 S02 不是互相取消的普遍规则，路线取决于可测性和支持承诺。
- **条件：**缺少可信夹具、版本支持范围或可行的覆盖路径。
- **核验：**`not_evidence`。这是一个条件化的讨论路线，不是目标案例的最终建议。

## S04 — 自信的经验报告，但没有可复核材料

- **报告主张：**虚构角色 R3 声称，在某次 Forge 输出格式迁移中，分阶段试放时有一款插件先暴露格式不兼容，因此避免直接全面发布；R3 对自己的记忆很有把握。
- **类型/来源：**`experience_claim` / `claimed_firsthand`，由模拟角色给出。
- **来源/独立性：**仅一个被声称的记忆；`independence_group: unknown`。重复这个故事不能变成第二个独立来源。
- **缺失材料：**没有日期、版本号、工单、CI 输出、命令、影响范围或其他可核查来源。
- **核验状态：**`unverified`。主持人保留该报告主张，但不得把它当成已经证实的成功案例，也不得估算成功率。
