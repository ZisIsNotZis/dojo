# 已实现的三幕 Demo：说明与验收边界

## 来源与确认状态

本页记录 `python3 -m dojo demo` 已实现的三幕陌生人故事的方向、台词与验收边界；角色台词与具体交互仍是待实现、待检验的设计，不是用户研究或已观测效果。**产品方向以 [product.md](product.md) 为准**，本页不是产品方向入口。

## 产品目标

道场服务互不认识、分别面对自己问题的陌生人。用户可以同时或先后使用，不属于同一团队、不共享同一项目，也不需要直接交流。通过匿名道藏连接的是方法论、理由、前提、适用边界与异议，不是私人对话、个人身份或项目细节。

主题应自然、可理解，例如空间整洁、软件开发方法、开始行动、维持执行、减少无用功。主体验不是共同排查某个虚构软件的技术故障。跨领域迁移可以展示价值，但不要求所有有价值的连接都跨领域。

纯抽象思考可以贡献新洞见，不以真实实验作为入场前提。自洽不等于真实，经验自述不等于核验，重复传播不等于独立证据。冲突可推动边界澄清；不强行给唯一答案。通用道与具体应用必须区分，具体场景不能覆盖原来的抽象洞见。其他理念见 [philosophy.md](philosophy.md)。

## 已确认的新版故事方向

三位陌生人分别进行独立对话；一个操作者可以演练三位角色，无需招募真人。

| 角色 | 独立问题 | 道场中的作用 |
|---|---|---|
| 甲：空间整洁 | 维持整洁不能只依赖自律；物品归位太麻烦会使收纳难持续。 | 提出候选方法论：让一种行为持续发生，除提高意愿，也可降低正确行为的摩擦。讨论安全步骤、美观与空间等边界。 |
| 乙：软件开发 | 经常先写代码后发现需求没想清楚，考虑强迫自己先写完整需求文档。 | 借用上述理由，比较完整文档与低成本澄清：先明确给谁用、解决什么、怎样判断做成；保留复杂、高风险、多人协作时需要充分分析的路线。 |
| 丙：抽象挑战 | 某些能力靠困难练出来；把一切变容易未必有益。 | 讨论并区分减少无谓摩擦与保留有意义的训练难度，补充原道边界，不将其简单判错或删除。 |

上述故事不是已执行结果。乙不可见甲的私人房间故事；获得的是提炼后的理由及条件。丙不需要实验报告也可提出有效的逻辑挑战。

## 端到端验收要求

1. 一命令、中文、可理解的陌生人故事；不需要读 JSON 或了解协议、夹具等技术背景。
2. 清楚展示每位用户说了什么、助手追问什么、为什么提炼为此候选；贡献者可确认、编辑或拒绝，不默认同意。
3. 经同意才保存；在另一个独立问题中真实检索、带回候选，解释相关性与不适用条件，不硬套、不假造语义检索。
4. 保留不同方法路线和具体未知；挑战后真实保存版本或关系，保持通用道与应用分离，不因整洁而强制合并。
5. 预设台词、历史模型回放、即时模型生成明确区分；预设故事不假装理解任意输入。
6. 测试与模型演练记录来源，不能将合成用户当真实用户研究或将单样本当效果证明。
7. 用户在远端，只能看聊天文字。交付必须直接在聊天中详细展示角色、逐步对话、选择、保存与演化；运行命令或文件路径不能替代展示。

## 当前实现与证据边界

当前 `python3 -m dojo demo` 已按本页的三位陌生人故事实现：甲（空间整洁）→ 乙（软件开发）→ 丙（抽象挑战），一命令、中文、逐步可读；只展示并保存提炼后的理由与条件，不保存私人场景；检索用真实 `Store.retrieve`；挑战产生新版本与关系而不删除旧道。预设台词、历史模型回放（`compare`）与即时模型（`chat`）三种模式在体验开头明确区分。

仍属模拟，不构成效果证明或用户研究：

- 甲/乙/丙都是写死的预设台词，不解自由输入，也不代表真实用户。
- 检索是透明词汇重合，不是语义检索，也不证明两个问题同源。
- 三幕 Demo 落地当时有 27 项标准库测试通过；测试覆盖流程与存储，不等于产品效果。当前测试面看 `python3 -m unittest discover -s tests`，不引用这个旧数字。
- 真实 Pi Luna B/C 输出是旧 editor-bridge 评价的归档，仅供 `compare` 回放，不证明道场胜过普通 AI，也不属于本页新故事；HTTP adapter 仅经 loopback mock 测试，真实远端服务仍未验收。
