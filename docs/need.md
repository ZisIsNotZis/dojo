# 需求

本文描述"什么必须成为真"，是痛点层与产品层之间的需求入口。每条需求都指向它服务的痛点。

## N1 用户零结构负担（服务 P2）

- 用户唯一的显式动作是说自然语言。不得要求用户创建、确认、编辑、维护任何卡片、表单、版本或状态。
- 入库默认无需用户显式许可，可作为全局开关 opt-out；当前阶段不实现该开关，但架构必须预留。
- 可观察：一次完整会话中，用户输入中结构化指令（y/n/命令）的出现次数为 0。

## N2 引导出带边界的结论并自然对齐（服务 P1、P3）

- 主持人必须主动引导，而不是被动应答；引导目标是产出带适用范围、前提、替代路线与未知的表述。
- 对齐以对话完成，而不是表单确认：双方就一个带边界的表述自然达成一致，用户一句"不对，因为……"即可推翻。
- 可观察：会话结束时产出的结论包含 `scope`、`premises`、`alternatives`、`unknowns` 四项内容，且对话中存在用户的反驳或修正痕迹。

## N3 真相优先于用户满意（服务 P3）

- 面对用户坚持的错误主张，主持人不得以让步解决冲突；只能以更软的措辞、更好的引导解决冲突。
- 不得伪造事实、引用、实验或亲身经历。探针只能作用在概括的尺度上，且事后披露。
- 可观察：负控制场景中主持人不让步且不失礼。

## N4 结论无声入库且可追溯（服务 P1、P5）

- 会话达成的结论由主持人写入后台，附带出处（哪次会话）、独立性标记与范围边界。
- 库中记录的是"双方在某场景某约束下达成的共识"，不是"为真"。
- 可观察：入库条目的 `source`、`independence`、`scope` 字段正确，且用户未做任何显式确认动作。

## N5 跨用户广播回流为讨论材料（服务 P4、P5）

- 新会话应能把库中他人独立得出的相容或相反主张，作为讨论材料带回来，由主持人转述。
- 检索必须忠实：只报告真实命中的词，不假装语义理解，不夸大相关性。
- 可观察：带广播与不带广播的对照会话存在可辨识差别；检索报告与底层命中一致。
- **现状（2026-10-23）：只有一个人的材料，因此这一条没有任何跨人证据。** 它仍是需求，不是已实现；第二份材料是模拟语料，按 `docs/dao/README.md` 的规矩只标 `模拟`，不算第二个人的证据。

## N6 体验不低于现有聊天产品（服务 P2、P3）

- 用户感受的有用性与易用性不得低于 DeepSeek、豆包一级的聊天产品。
- 具体：零表单、纯文本、会话内无明显仪式感、等待时间可接受、失败有清晰降级。
- 可观察：一次会话的用户动作数与表单数为 0；失败路径有明确提示而非静默错误。

## N7 后台可扩展、可配置（服务 P5）

- 后台管线必须在不改代码的前提下增删处理步骤、调整顺序与写入策略。
- 每个处理步骤必须幂等、可恢复、留事件记录。
- 可观察：改配置 manifest 即改变管线行为；重跑同一会话不产生重复版本。

## 非需求（明确排除，防范围蔓延）

- 不建 UI、社交网络、公开排行榜、常驻服务、计费系统。来源：用户自述（`../idea.md` 第 4 节）。
- 不做多节点联邦与公开注册；阿里云部署与 token 商业模式在价值环被证明之后再议。来源：用户自述（2026-10 对话）。
- 不以合成角色扮演代替真实用户研究，不把单样本当效果证明。
- 详见 `product.md` 的质量维度与非目标一节。
