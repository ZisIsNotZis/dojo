# 走一遍：一句话带着它的边界，过几天被另一场讨论引用

2026-11-28，干净检出即可重跑。这一段只改屏幕和交付块，不改库结构，不发外部请求；
用到的模型是一个本地回环桩，脚本写死的回答**不是**真人结果，也不是模型判断。

下面每条命令都在仓库根目录执行。旧屏幕摘录保留作历史对照。

## 0. 一步看到全貌

```bash
python3 docs/evidence/2026-11-28-handoff-boundary/story.py
```

它把三场连起来走一遍并打印真实屏幕：第一场他说出并认可一句带边界的话 → 第二场
`--card` 在模型开口之前读到它 → 有人 `challenge` → 第三场读到那句质疑。结尾是读数。
离线，17 项，退出码 0 表示全部成立。

要严格的版本（逐项断言、计数）：

```bash
python3 docs/evidence/2026-11-28-handoff-boundary/verify.py     # 45 项
python3 docs/evidence/2026-11-28-handoff-boundary/redarm.py     # 8 条红臂
python3 -B -m unittest discover -s tests -q                     # 全量
```

## 1. 自己用 CLI 走（接一个真端点）

真实会话需要一个 OpenAI 兼容端点：

```bash
export DOJO_LLM_BASE_URL=... DOJO_LLM_MODEL=...
DB=$(mktemp -d)/walk.sqlite3
python3 -m dojo --db "$DB" discuss
```

说一句你的经验（例如「值班提醒交给系统跑，只在结果会打断他时才叫醒他」），主持人会把它
写成一条候选。先读程序展示的完整版本；同意才单独输入 `/认可`（认可不等于验证）。
然后它问四件事（情境/张力/代价/失效），答完退出。

## 2. 第二场：把那张卡交给另一场讨论

```bash
python3 -m dojo --db "$DB" list                  # 找到卡片 ID
python3 -m dojo --db "$DB" discuss --card <ID>
```

**在模型开口之前**，屏幕上应该已经能看到这些行（这就是这一段交付的东西）：

```
这一场带上了一张以前写下的卡 <ID>，状态：草稿。
  「值班提醒交给系统跑，只在结果会打断他时才叫醒他。」
  库里有这套说法（句子连同它写的条件）的认可记录：有人在讨论里认可了这套说法（2026-11-28）。…
  什么时候成立：「他已经抽身、这条提醒的失败不会当场伤人时」
  什么时候不成立：「提醒必须发生在值班当场、人来不及时接手时」
  还没定的是：「他会不会真的回来看提醒」
  它靠这些前提：「系统能自己跑检查」
  它有 1 条来源记录：他自称亲历、未经核验。这是记录条数，不是人数；核验状态如上，不代表这句是真的。
  - 他自称亲历、未经核验：「他这样值过两次班」（他自己限定：「两个班次都在同一个组」）
  这场里它是资料，不是你说过的话。…
```

四件要能一眼分开：**什么时候成立 / 什么时候不成立 / 还没定的是 / 它靠这些前提**。
库里有几条就印几条；没写过的字段不印（不是印「没有」）。

## 3. 有人质疑它

```bash
python3 -m dojo --db "$DB" challenge <ID> --text '第三个团队里更糟：提醒他根本没看'
python3 -m dojo --db "$DB" show <ID>        # status=challenged，contradictions 多一条
```

再开一场 `discuss --card <ID>`：那句质疑出现在「什么时候不成立」下面——它进的是同一个字段，
所以和原来的反例并列，不需要另一条通道。

同时「认可记录」那行会变成「库里没有这套说法…的认可记录」：质疑改了这套说法的内容，
之前那条认可就不再代表它了。这不是数据丢了，是**认可绑的是内容，不是句子**。

## 4. 改过说法之后再来一场

```bash
python3 -m dojo --db "$DB" revise <ID> \
    --statement '值班通知都先等两次失败再呼叫负责人。' \
    --reason '这次想把做法试着推广到所有值班通知。'
python3 -m dojo --db "$DB" discuss --card <ID>
```

屏幕应当说（注意这次改动是**变宽**的）：

```
  库里记着这一句换过说法，之前是：「只有普通日报才等两次失败再呼叫负责人。」
  库里记下的改动理由是：「这次想把做法试着推广到所有值班通知。」
```

**不**说「它比更早那句窄」。旧句子会说成变窄，紧接着再把变宽的理由念给你听。
`revise` 行记的是「从哪句、为什么」，不记方向，也不记是谁改的。

## 5. 续谈同一场

```bash
python3 -m dojo --db "$DB" discuss --resume <这一场的轨迹文件>
```

开场印的交付块要和第一半**一字不差**：边界、来源、认可记录都在。它从轨迹里的 `handout`
行重建，不查库——中途要是有人改了这张卡，这一场仍然在说它开场时那一版。

## 6. 这些读数在说什么

`story.py` 与 `verify.py` 的期望读数（改后）：

| 读数 | 第二场屏幕 | 发给模型 |
|---|---|---|
| 原句 | 有 | 有 |
| 什么时候成立 | 有 | 有 |
| 什么时候不成立（含质疑原话） | 有 | 有 |
| 还没定的是 | 有 | 有 |
| 来源记录说的是什么 | 有 | 有 |

改前，上表四行边界是「屏幕没有 / 模型有」，而 `draft` 会在库里明明有 `wording_accepted`
的时候告诉你「这一句还没有人认可」。改前的读数由 `git show <父提交>` 取旧树后跑同一批
脚本得到；`SUMMARY.md` 里列了那时的表。

## 7. 这一段**没有**做的事

- 屏幕不印 `alternatives`（另一条路）。它帮不上「我这边要不要照做」这个决定，五行边界
  加上一条路线会把句子本身埋掉；`show` 和模型那边照旧有。
- 不做「哪一句是谁说的」的推断。卡片上分不出来时就不说；第一场收尾已经说过「字这一版
  仍全算我写的」。
- 不判方向，也不判谁该信谁。屏幕只重复库里记的字段和事件。
- 没有真人参与。上面所有「他」都是脚本写死的桩回答。
