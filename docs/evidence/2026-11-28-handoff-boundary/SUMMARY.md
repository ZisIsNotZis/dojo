## 这一片回答的问题

监督者给的题：「一句话经验经过提问澄清、留下明确边界，过几天被另一场讨论正确引用和质疑。
希望当事人不用先翻账本就能看见条件、反例和来源，再决定这条经验能不能迁移。」

上一片（`2026-11-28-card-handoff`）已经把**那句话**交给了下一场。这一片量的是：**它的边界
到没到人眼前。**

## 改之前实测

改之前的读数是在父提交 `805281e` 上量的，用的是我当时留在 `.scratch/3419/` 的探针
（那两份**不随版本发布**，所以这里不把它们当入口）：`probe_boundary.py` 把一张带
`scope`/`contradictions`/`unknowns` 的卡交给第二场，`probe_story.py` 把三场连起来走。

要看这两份脚本的可复跑版本，用现在发布在 `docs/evidence/2026-11-28-handoff-boundary/`
里的 `story.py`：它在**当前树**上跑出改后的读数，`git stash` 或取旧树后跑同一份脚本，
就能得到改前的读数。改前那三行是：

| 边界 | 第二场屏幕 | 发给模型 |
|---|---|---|
| 范围（什么时候成立） | **没有** | 有 |
| 反例（什么时候不成立） | **没有** | 有 |
| 未知（还没定的） | **没有** | 有 |

同一批脚本把三场连起来走（第一场他认可一句带边界的话 → 第二场 `--card` →
`challenge` → 第三场 `--card`），又量出两个同类缺陷：

1. **状态词的括号是猜的。** 第一场收尾说结论被认可（库里 `time_basis.acceptance_path=
   discuss_conclusion`），第二场开场印的却是 `草稿（这一句还没有人认可）`。
2. **质疑没有单独通道。** 质疑进的是 `contradictions`，所以它和反例同一个字段——但那个
   字段根本没印到屏幕上，于是「这句被质疑过」只剩状态词，而状态词后面跟着的
   「质疑之后还没有人再认可」同样没人查过（后来的认可不会把 status 从 `challenged` 挪开）。

监督者独立复现了两条，用的材料与我的不同：一条读数是第二场屏幕上 `scope`/`counterexample`/
`unknown` 全为 `false`、发给模型全为 `true`；另一条是**改宽**的卡被印成「它比更早那句窄」，
紧接着念出改宽的理由。

## 改了什么

`handoff_block()` / `handoff_for_model()` 共用一次读数，屏幕和模型不可能各说一套：

- **边界逐行印。** 什么时候成立 / 什么时候不成立 / 还没定的是 / 它靠这些前提，每条一行，
  库里有几条印几条，照原话。空字段不印（不是印「没有」）——和 `time_basis` 同一条规矩。
  质疑进来的反例和原有反例并列，因为它本来就是同一个字段。
- **认可记录单独成句，由 `store.has_acceptance` 那条链回答。** 有就说有、走的是哪条路、
  哪一天；没有就说「库里没有这套说法（句子连同它写的条件）的认可记录；这不等于没人认可
  过它，只等于这个库里没记下」。
- **状态词只说自己。** `draft` 印「草稿」，「可讨论」印「有人把它标成值得讨论」——后者不是
  认可记录，共用一个词会让同一屏自相矛盾（我第一版就撞上了）。
- **改动只报库里记下的。** 「库里记着这一句换过说法，之前是…」+「库里记下的改动理由是…」。
  `revise` 行记了从哪句、什么理由，**没记方向，也没记是谁改的**，所以「变窄」和「他改主意
  时说的是」都去掉了，导出那条 `revision_left_wording` 一并改。
- **来源逐条印。** 数量与核验状态之外，再印每条记录主张什么、写它的人自己限定了什么；
  超过 4 条就印「还有 N 条没印在这里，可以看这张卡本身」——计数，不概括。
- **`alternatives` 不上开场屏幕**（刻意的取舍）：它帮不上「我这边要不要照做」，而五行边界
  已经够长。`show` 与模型那边照旧有。

### 续跑

`handout` 行多带一个 `acceptance` 字段（有没有这条记录、走哪条路、什么时候）。续跑从**轨迹
行**重建这一块，不查库——库里后来改了这张卡，这一场仍然在说它开场时那一版，认可记录也一样。
旧轨迹没有这个字段就什么都不印，那是「这份记录里没写」的诚实读法。

## 这一片里我自己犯的三个错

1. **第一版把「认可」用在两处。** 状态词说「有人认可它值得讨论」，紧挨着认可记录那行说
   「库里没有认可记录」。同一屏自相矛盾，`probe_boundary.py` 一跑就看见了。`confirm` 不是
   接受措辞，词得分开。
2. **`verify.py` 的头一版有三个洞。** fixture 里先 `confirm` 了卡，于是 `draft` 那条路径
   和「从轨迹行重建」那条路径根本没被走到——三条臂是绿的。改法是加一张**保持草稿却带认可
   记录**的卡，那正是缺陷本来的状态；再把续跑那两项改成按卡 id 找轨迹，而不是取最新的那份
   （新加的两场把「最新」变成了另一张卡的轨迹，检查沉默地量错了文件还一直是绿的）。
3. **一条红臂靠崩溃变红。** 手工的探针脚本里 `fields` 少了字段会 `KeyError`；那不算检查看见
   了缺陷。改成先断言形状再取值。

## 仍然开着的

- **「收下」的语义**（旧记忆里那条）在这一片没有被迫定：`no_instance` 与边界语义没有交叉。
- **认可与质疑的先后关系**没有新出口。现在一屏能同时看到「被质疑过」和「有过一条认可记录」，
  但两件事在时间上的先后仍然只在 `show --history` 里。如果下一片要让人判断「这句是在被质疑
  之前还是之后被认可的」，得先把这两个时间放进 `time_basis`，而不是让屏幕去猜。
- **一次只能交一张卡，得知道 id。** 没有「按那句话检索」，这一片没有动它。
