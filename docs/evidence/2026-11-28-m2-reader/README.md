# M2 独立读者验收：误判类能否从清单发现

2026-11-28，候选树基于 `6bae274`。要回答的问题：当模型给出一个**听起来合理、引用的字也真说过、却没有支持该分类**的提议时，读者能不能只从清单发现它、并知道哪些内容值得保留。

材料全部是本地合成讨论，模型是回环桩。这里验证的是**清单显示是否忠于材料**，不是桌游实践是否发生，也不是真实模型分类质量。

## 场景

真实 CLI `discuss → pipeline --classify → distill --text` 走一场合成讨论：

- v1 用户说「**想试**在桌面放一张卡……」并明说「先把这说成试法，不是结论」，v1 获认可时的讨论候选是 `application`。
- 模型桩故意把它错标成 `experience_claim`，理由称「实际用法」，引文逐字存在，但**恰从「想试」之后开始**。
- v2、v3 是正确的 `experience_claim`、`question`；另有未认可草稿一条。

## 两阶段盲读（未看实现）

1. 只读**修复前** `distill --text` 时，读者会留 v1 的做法和适用范围，但没有认出「经验陈述」是错判。他能看出 v2 只引了第二次彩排，并质疑近邻关系和版本标记。原始记录：工作区 `.scratch/3630/blind-reader/first-read.md`。
2. 同一读者沿清单轨迹复查，确认 v1 是试法被升格为经验，并建议保留承诺强度，两个类型不一致时标待核。原始记录：工作区 `.scratch/3630/blind-reader/trace-read.md`。

因此优先让清单自己展示判类所需的原话，而不是先改版本编号或近邻导航。

## 修复后复核

修复内容（`dojo/pipeline.py`、`dojo/distillation.py`）：

- 讨论候选类型与模型提议不一致时，标题改显「判类待核」，不再直接印更强的那一类；
- 说明行写明「讨论时为 X；后续模型提议为 Y」，并指出「认可表述不等于认可判类」；
- 原话分两行：`模型摘录` 与 `原话整轮`（或 `原话开头（已截短）`），截短时显式标出；
- 依据缺口改称「模型指出的依据缺口」，避免读成工具已核定。

第二位读者只看新版 `distill --text`，没先看本轮旧输出或首读结论。他据整轮原话驳回 v1 的经验标签，保留试法、v2 限于两次彩排且不作归因的亲历观察、v3 待验证问题，并把草稿排除。他指出模型给的依据缺口不完整：连单组实际用过都没报告，并非只差双组数据。最后一版把缺口明确归给模型，没有替它补判。原始记录：工作区 `.scratch/3286/legacy/readback-3630.md`。

## 仍不能声称

- 回环桩只证明显示与绑定，不证明真实模型的判类质量。
- 「想试」这一处是手选的对抗样例，不代表误判率。
- 「判类待核」只提示两个标签不一致，标签一致也不代表原话支持它；引用以外的上下文、认可轮细节和跨场近邻仍需查原记录。
- 无获准模型线路，没有访问真实模型或读取宿主配置。改文案前全量回归 1403 项通过；最终文案已随真实 CLI 离线重放再验。
