# 真实模型验收：从订单导出经验到月末对账，再续跑

2026-11-28；发布基线 `68dbda9`。主持人是 DeepSeek `deepseek-flash`（真实 API，请求 `medium` / `json_object`）；讲述者是同一个脚本模拟角色，不是真人。订单、客服反馈、工时与财务场景都是合成的；没有向模型发送业务记录，也没有执行真实对账。记录器转发实际请求，不代答。工作区只收摘要与检查器，不收原始请求、模型输出、会话或库。

## 体验判断：主链能走通，提炼仍需人核对

- **先立卡。** 合成案例里，客服对着一条能点通的订单导出路径提出两处具体歧义：退款时间口径、文件归属。模型整理出适用于低成本原型、需求未定且使用者能试的结论；保留「提前一周」是反事实估计、单路径不证明覆盖率、文档评审也可能发现问题。`discuss` 写下认可记录与四个附答槽，认可没有变成事实核验或 `confirm`。这张卡仍有可以质疑的地方：模型把「只打通一路」读成了「成本低」并标成用户陈述；脚本提前排入的认可句还落进了情境槽，之后几句错位。回执准确记了输入原字，但 4 个槽不等于 4 个答到点的回答。
- **换到对账。** 反例是对方无运行环境，只看截图给了泛泛好评；新场景同样不能自己运行，但财务可以对照已知结果逐行核对差异表。主持人区分了可迁移的部分（用具体条目检查匹配、时间窗口和输出口径）和不能迁移的部分（谁触发、权限、失败能否被发现、其他月份/路径的覆盖）。只回复「收到」而没核过具体条目，不是验证。模型没有证明新办法会更快；它也一度给出了素材未支持的人数和工时推算。这个结果适合作为下一步怎么核的建议，不是已验证的工作经验。
- **落卡和来路。** 发布基线在迁移场耗尽 12 次请求，无认可写入；缩小空回复重试后，另一次相同输入从原卡开场，5 次请求写下迁移卡。用 `show` 查到 `derived_from`，用旧卡关键词 `search` 读到反向链接；没有把旧卡替换、新卡判作「变窄」、或把这场当独立佐证。两次输出由真实模型生成，不能把 12→5 归因于补丁，脚本后续输入落入的模式也不完全相同。

## 续跑：实测缺口与修复

从迁移场打印的 `transcript` 路径续跑，真实开屏和实际出站请求都保留了原卡措辞，却都遗漏 4 条附答。原因是开场快照有来源记录、措辞和边界，没存附答；续跑从快照重建。

修复后，新的开场快照保存当时已有的附答；续跑读它，不从当前库补写。没有这一字段的旧轨迹仍可续跑，但不会猜补旧附答。用已立的原卡在 `--no-profile` 下重新开场，EOF，**在库里另外改写原卡**，再 `--resume` 同一轨迹。真实请求次数 1 + 2（续跑第一响应空白，重试得到回合）。检查器从两次实际出站请求、开屏、轨迹和改写结果读回：

| 读数 | 开场 | 续跑（库已改写） |
|---|---:|---:|
| 原卡措辞、条件、反例、前提、未知 | 开屏与请求一致 | 开屏与请求一致 |
| 附答原字 / 数量 | 4，和卡片措辞分开 | 同 4 条，原字与来源不变 |
| 来源记录 | 1；核验状态不明，不是独立核验 | 同 1 条 |
| 卡片块与本轮发言分开 | 是 | 是；无较新措辞 |

两次实际出站请求的卡片材料块逐字相同，SHA-256 `1e04640a389d62cde300ce5d685755b898181840fb7d403deea68b59057cf1af`。开场与续跑各读自同一条 `handout`，没有写第二条开场记录。`alternatives` 是模型可见但开屏按既有设计省略的三条备选，可用 `show` 阅读；上表不是「全屏和整个请求逐字相同」。

## 空回复的范围

立卡正式段 9 个请求中 5 个返回空白，基线迁移段 12 个请求中 7 个返回空白、两个回合最终未得到模型有效回答。服务端 `finish_reason=stop`，但 `content` 无可见字符；这不能证明服务端为什么返回空白。小批重放中，无修改的 6 次没有一份通过内容校验；通用纠正行先有 4/6 通过，另一次是 0/5；明确点名空白的重试也是 0/5。另几组探针没有建立更可靠的模式，不能推断提示词提升成功率。

这里只做请求预算修复：同一回合空回复至多纠正一次，仍受既有轮内与会话上限约束；严格 JSON 校验不放松，不把散文或推理当作可写卡回答。测试用连续两次 `empty_content` 证明旧规则花 3 次、新规则花 2 次并让下一轮继续；不是服务端修复。验收期间含探索探针共 128 个聊天请求尝试（按发起计，包含一次连通性检查，不是 token 或账单读数）。

## 如何复核

干净检出中，不需要网络：

```sh
python3 -m unittest tests.test_card_handoff tests.test_handoff_boundary tests.test_discuss -q
```

`test_resume_keeps_attached_answers_after_the_library_changes` 在两段之间撤下并替换一条附答，同时检验续跑屏幕和模型请求仍见旧话、不见新话。`test_a_blank_reply_is_retried_once_and_never_with_the_same_bytes` 钉住连续空回复的花费。发布版的固定回复对照还在 [派生关系演练](../2026-11-28-derivation-edge/WALK.md)。

线上重跑须有自己的获准线路和预算。设置 `DOJO_LLM_BASE_URL`、`DOJO_LLM_MODEL`，在本机通过密钥存储设 `DOJO_LLM_API_KEY`（不要写入命令、库或证据）。用新临时库运行：

```sh
umask 077
LAB=$(mktemp -d)
DB="$LAB/dojo.sqlite3"
python3 -m dojo --db "$DB" discuss --no-profile
```

讲上述虚构订单导出故事：只一条主路径、客服当天能实际试、发现退款口径和文件归属两处歧义。明确「一周」只是估计、一次只看截图的好评没有后续。等主持人给出**确切的带条件结论**，认可它时说清所认可的内容。看到实际提示再逐题答，不要预排四句话；从收尾抄卡 ID。用 `show` 核对附答和接受记录，再走 `discuss --no-profile --card ID`，提出无运行环境而可逐行核对的月末对账。EOF 后，另开终端 `revise` 原卡，用一条显眼的新说法作为对照，然后用收尾的 `discuss --resume TRACE --no-profile` 续上，检查屏幕仍是开场旧卡。不要把另一场的最新条件当成旧卡的新事实。

有权限查看本次私有记录的复核者，可用 `python3 docs/evidence/2026-11-28-live-blank-reply/check_private.py PRIVATE_RUN_DIR` 重算上表的实测读数。新录制时使用获准的回环转发器按原样向真实线路发送请求；检查器需要每段 `stdout.txt`、含已转发 `request` 和 HTTP `status` 的 `requests.jsonl`、同一轨迹与 `revision.json`，不需要凭据、响应正文或推理。它只打印判断与计数，不打印原文。
