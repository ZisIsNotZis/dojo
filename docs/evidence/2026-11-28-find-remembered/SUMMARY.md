# 2026-11-28 — 过了几天，只记得大意：找到那张卡，先看它适不适用

## 一段话

`dojo search` 以前把人当成调用方：打印整张卡的 JSON，一条判断都没有。一个人过了几天，
只记得那句话的大意，他要的是「找到值得看的那条，先看它适不适用，再带进新讨论」。
这一片把那个出口改成人的屏幕（stderr），JSON（stdout）逐字不变：

- 每张对上的卡都印句子、四条边界、来源记录、认可记录，和一条可粘贴的 `discuss --card` 命令；
- **检索不会交出去的卡不再消失**，就排在同一条清单里，各自说明为什么（被质疑、被撤回、
  没有认可记录、认可绑的是旧说法）；被质疑的那张还会把质疑原话印在「什么时候不成立」下面；
- 记得的是**改掉之前**那句也能找到，并说明「这是它以前的说法」；
- 一个字都对不上时，先说清方法（只比字词，不认意思），再给「最近写下的卡」作为
  **另一个办法**，并说明它不是按意思找的。

## 交付前实测到的三件事（都在标准 CLI 上）

| 症状 | 实测 | 这一片之后 |
|---|---|---|
| 被质疑的卡从检索里无声消失 | 质疑前 1 条命中，质疑后 `results: []`、exit 0、无任何解释 | 仍在清单里，标「被质疑过」并印质疑原话与条件 |
| 改过说法的卡用旧句子找不到 | `search '日报连续两次失败后才呼叫负责人'` → 空 | 命中，并注明是它以前的说法、现说法是什么 |
| 只记得大意时屏幕什么都不说 | `results: []`，没有一句方法说明 | 说清只比字词，并给出最近写下的卡（标明不是匹配） |
| 用相对路径指定库时，屏幕给的命令换个目录就失效 | `Store.path` 原样是 `lib.sqlite3` | 打印前解析成绝对路径（#3419 的规则） |
| 终端上 24 行屏幕后面紧跟 48 行 JSON | 屏幕最后一行的命令被淹掉 | stdout 是终端时不印 JSON，只留一句怎么取 |
| 旧说法那条注说「下面这句是它现在的说法」 | 现说法印在上面，方向词把新旧指反 | 改指「本条目开头引的那句」，不再说方位 |
| 指到一个不存在的库时被当作空库 | 静默建库，然后印「没有一张卡的字和这些词重叠」 | 拒绝并说库不存在，不建文件 |
| 「对上 N 个词」对上了卡里的别处 | 卡说「值班通知交系统跑。」，条件是「越限会当场损坏货物」，搜后者得到「对上 8 个词」紧接着一句毫无重叠的话 | 条目说明字在条件/反例或来源记录里，并说清那句本身没重叠 |
| 新的检索键漏进机器输出 | 每行多了 `matched_in`（只查最外层四个键和两个具名键都看不到） | `READING_ROW_KEYS` 一处定义；读数把整行与模型那面逐键比 |
| 只在 alias 上对上也说成现在这句对上 | 现在那句重叠 0 个词、alias 重叠 5 个词，`matched_on` 仍是 `current`，屏幕上一句注都没有 | 把对上的 alias 原样印出来，并说明卡片现在那句没重叠 |
| 只引用了这句话的卡排在说这句话的卡前面 | 两张都是 16 个词，按 id 排，条件里抄了那句的卡排第一 | 屏幕先排本条目自己的那句，再按词数；屏幕自己说了这个顺序 |
| 检索改写了它只看一眼的文件 | `0444` 的库搜完变 `0600`；别人的 SQLite 库里多出四张 dojo 表 | 只读打开：权限、字节、表都不动，别人的库当场拒绝 |

复核者在一个发布版小库上复现了更糟的一种：两条卡都说「值班通知、打电话」，质疑自己的那条之后，
同样的词只剩**恰好相反**的那条 —— 剩下的清单看起来像是完整的答案。现在两条都在，各自说明。

## 字对上的是卡里的哪一块（560a07d 之后补的一段）

这一段是同一个缺陷的另一面。屏幕一直在说「这张卡的字和这些词重叠」，而检索比的是整张卡：
句子、alias、前提、条件、反例、来源记录一起比。于是屏幕把「条件里有你这几个词」读成
「这张卡说的就是你要的」——三种实测：

- 卡说「值班通知交系统跑。」，条件是「越限会当场损坏货物」：搜后者得「对上 8 个词」，
  紧跟一句亜无重叠的话。事实都在屏上，几句之间的话没有。
- 只对上 alias 时 `matched_on` 返回 `current`，一句注都不印。实测：现在那句 0 个词，
  alias 5 个。
- 两张卡都是 16 个词，按 id 排，把条件里抄了这句话的卡排到了真正说这句话的卡前面。

现在每条注印的是字在哪一块（`matched_in`：sentence / alias / limits / sources / earlier），
屏幕先排本条目那句先排、再按词数。`matched_in` 只在 `for_reading` 时加，模型那一面不多出一个键。

### 监督者抓到的一条，值得记下来

上面那句「模型那一面不多出一个键」是**写完之后才成立的**。第一版把 `matched_in` 加进
了 `for_reading` 的行，却没把它加进 `cli.py` 的剔除名单，于是**每一行机器输出都多了一个键**。
我自己的契约读数当时是绿的——因为它只查最外层四个键，再加两个具名键，新键两个都不碰。
监督者是**把输出接进程序逐行看**才看到的。

所以现在：屏幕用的键名在 `storage.py` 里只写一处（`READING_ROW_KEYS`），`cli.py` 用它剔除；
读数不再点名单，而是**在同一个库上同时命中正文/条件/alias 三种行，把命令行 stdout 的每一行
与模型那面同一张卡的行逐键逐值比**；臂 `a-new-reading-key-leaks-into-every-published-row`
复原原来的剔除名单，红的就是这条读数。

自己再跑一次逐行对照（不需要端点）：

```bash
python3 docs/evidence/2026-11-28-find-remembered/verify.py | grep 逐键
```

## 屏幕的判据（与上一片相同）

屏幕上任何一句替程序说了它没查过的事，就是缺陷。所以：

- 拒绝的原因来自账本的事实（`status`、`contradictions`、`wording_accepted` 事件是否绑定当前这句），
  没读出来就说「具体原因这次没有读出来」；
- 「这个库里没有认可记录」后面必须接「这不等于没人认可过它」；
- 拒绝之后必须接「这不等于库里没有它」，因为紧跟着就是那张卡本身；
- 「最近写下的卡」必须说清是按写入时间，不是按意思；
- 字在哪一块必须说清，不能把条件或 alias 里的重叠说成「这句对上了」。

## 读数与红臂

```
python3 docs/evidence/2026-11-28-find-remembered/verify.py   # 64 项，0 不成立
python3 docs/evidence/2026-11-28-find-remembered/redarm.py   # 22 条臂
python3 -B -m unittest discover -s tests -q                  # 全量
```

22 条红臂各自复原一处旧行为，并且必须红在**自己那条检查**上。它们已经抓到四类假绿：

1. 检查用裸短语「被人质疑过」，而状态行里也有这几个字 → 拒绝行丢理由也照样绿；
2. 检查只看「id 出现在屏幕上」，而空结果的「最近卡片」清单也印这张卡；
3. 检查取「第一条命令」，而排序按词数，第一条可能是相反那条的命令；
4. 探测脚本用一句和现说法共享大半字词的话去测「旧句子可搜」—— 那段本来就能搜到，
   臂因此一直是绿的。现在用只在旧句子里出现的词（`只有普通日报`）。

另外，写测试时抓到我自己的一处真缺陷：`_withheld_basis` 一开始把整本事件账本当成认可事件，
于是**任何** `add` 出来的草稿都会被说成「有人认可过它以前的说法」。

## 机器读的那一面

`Store.retrieve(query)` 不带参数时逐字同上一版；`search` 的 stdout 仍是四个键、每行键不变
（屏幕用的 `withheld` / `recent` / `matched_on` / `matched_wording` 在打印前去掉，也不进模型上下文）。
`verify.py` 的 F 段两头都查：命令行 stdout，以及进程内那次给模型的检索。

## 只读是硬的

复核者在发布版上量到两个写：`search` 会把 `0444` 的库改成 `0600`，也会在一个只有
`stock` 表的别家 SQLite 文件里建出四张 dojo 表。原因是它走的是写入用的 `Store()`，
后面还跟一句 `chmod(0o600)`。现在 `search` 有自己的入口，`Store(..., readonly=True)`
打开：不建文件、不跑建表脚本、不 chmod、拒绝别人的库。唯一的写是读记录，而且只在
调用方点名了读者（`--session`）时才发生。`verify.py` 的 B5 段把三件事都量了：权限、
字节、表集合，以及那个文件在拒绝前后逐字节相同；红臂里三条对应还原。

## 宿主的机器入口

stdout 是管道或重定向时，`search` 仍打印与上一版逐字相同的四个键；只在 **stdout 是终端**
时不打印，改为一行提示（终端上给人看的不该被 JSON 淹掉）。宿主脚本原本就解析 stdout，
行为不变；唯一要改的是 `` search ` 直接对着终端跑的用法。`verify.py` 的 B3 段用 pty
两种情形都走了一遍。
