# 一条关于重试的经验，怎么改了这里的两个决定

材料：RFC 9110 §9.2.2（幂等方法）与 RFC 9112 §8（不完整消息），加本机实测。
日期：2026-11-27。基线：`d023b17`。证据：本目录；离线可复跑，联网只用于最初取回 RFC 正文。

| 材料 | 位置 | 它给的是什么 |
|---|---|---|
| RFC 9110 §9.2.2 | `source-excerpt.txt` 第一块 | 判断：幂等看的是**意图效果**，不是有没有写第二行日志 |
| RFC 9112 §8 | `source-excerpt.txt` 第二块 | 事实：响应不完整是可判定的，不必猜 |

## 1. 最初的说法：一条要记住的经验

第一次读到 §9.2.2，最容易被收成一句口诀：

> 有副作用的重试要小心。POST 不幂等，别自动重试。

这句话**不错**，但它不是判断，是记忆。和上一节 SQLite 主键那条一样，记忆没有边界，也没有后果模型：

- 它没说**怎么判**一件事是不是幂等 —— 靠方法名，还是靠效果？
- 它没说**日志算不算效果** —— 多写一行账，算不算「变了」？
- 它没说**什么时候可以自动重试** —— 连接断了就一定危险，还是只有某种断法危险？
- 它没说**用什么证据**判断 —— 猜，还是有可检测的信号？

四条都不是修辞。「别自动重试」这条口诀，在本仓会直接给出**错误**的结论，因为本仓有一个决定恰好相反。

## 2. 追问：这段话里哪一句是判断，哪一句是例子

原文有三句容易被跳过的判断，它们比口诀重要得多：

1. **「the intended effect on the server of multiple identical requests … is the same as the effect for a single such request」** —— 判据是**效果**。
2. **「a server is free to log each request separately, retain a revision control history」** —— 所以**多写一行日志不等于不幂等**。这一句直接否掉「重复就是错」。
3. **「A client SHOULD NOT automatically retry a request with a non-idempotent method **unless** it has some means to know that the request semantics are actually idempotent … **or** some means to detect that the original request was never applied」** —— 自动重试的条件是**有办法知道**，不是「大概没事」。后面还专门点了一句 **"Some clients take a riskier approach and attempt to guess"**，举的例子正是「连接在读到响应前就断了」。

第 3 条把问题从「能不能重试」换成了「**我知道什么**」。而 RFC 9112 §8 回答的正是这个：响应不完整**是可判定的** —— 按 Content-Length 收少了，或分块没收到最后一块。也就是说，这种情况下客户端**有**证据，只是本仓没用。

## 3. 把判断拿到本仓去量：两个决定

用同一段材料去问本仓的两个真实决定。两次都不是读代码得出的，是跑出来的（`probe.py`，全部离线）。

### 决定 A：模型响应读不完整时，要不要再发一次

`dojo/live.py` 的注释写着 *"do not retry"*，`dojo/discuss.py` 却对 `not_json` 自动重试两次。两者对不对，取决于一个事实：body 被截断时被归成哪一类。

实测（本地 stub + 真的客户端 + 真的讨论循环）：

| | 改前 | 改后 |
|---|---|---|
| 一次用户回合发给服务端的请求数 | **3** | **1** |
| 客户端给这种失败的种类 | `not_json` | `incomplete_response` |
| 用户被告知 | 「模型这次返回的格式不合法」 | 「响应在本机读完整之前中断……没有据此重发请求」 |
| 候选被写入 | 0 | 0 |

改前那三行里有两处错，且都不是「能不能跑」的错：

- **诊断错**：字节没到齐，被说成模型输出格式不合法。用户会去改 prompt 或换模型，而问题在传输。
- **动作错**：按 RFC，这正是「猜」——连接在读完响应前断了，就去重发。重发让模型把同一件事再做一遍，花的钱和产生的内容都是第二次的。

而且这条路的分类还漏了一档：分块编码的截断抛 `IncompleteRead`（被归进 `connect`），Content-Length 的截断**不抛异常**，只是 `read` 返回的字节比声明少 —— 只要不比对 Content-Length，就永远看不见。`probe.py` 里的 `_Cut` 用的就是后一种。

### 决定 B：同一个请求再来一次，账本要不要算新的一版

本仓自己的纪律写得很清楚：`docs/need.md:45`「每个处理步骤必须幂等、可恢复、留事件记录」，`docs/plan.md` 的验收项里有「同会话重跑管线幂等无副作用」，实现方式是 `pipeline_marks` 记「已处理到版本 N」。

实测同一个库、同一条命令跑两次：

| 操作 | 第二次 | 版本 | 事件 |
|---|---|---|---|
| `add` | rc 2，指名重复 | 不变 | 无 |
| `revoke` | rc 2，指名无有效确认 | 不变 | 无 |
| `unmerge` | rc 2，指名合并不再当前 | 不变 | 无 |
| `confirm` | **rc 0** | **2 → 3** | 多 1 条，内容与上次相同 |
| `challenge` | **rc 0** | **2 → 3** | 多 1 条，内容与上次相同 |
| `revise` | **rc 0** | **2 → 3** | 多 1 条 |

按 RFC 第 2 句，**多写一条日志本身不算错**。错的是后果：`pipeline_marks` 比的是版本号，版本被顶到 3，而标记还停在 2 —— 已经处理完的卡片**看起来又成了待办的活**，重跑管线会真的再做一遍。也就是说，第二次请求的**效果**与第一次不同，RFC 判据下它不幂等；而且从账本上也看不出第二次是重放还是用户真的又说了一遍。

这一条口诀给不出。口诀说「多写一条不算数」，照做就会认为现状没问题；只有读到判断①③、再拿 `pipeline_marks` 去比，才看得见后果。

### 决定 C：效果没变，就一定不是新请求吗

B 修完之后还留着一个洞，是复核时用真命令量出来的。同一张卡、同一句话，两次 `revise` 带了**两个不同的理由**：

```sh
python3 -m dojo revise c-one --statement '同一句话' --reason '移动端同伴看不见活动灯'
python3 -m dojo revise c-one --statement '同一句话' --reason '触屏读屏需要一个可读状态'
```

| | 改前（`ce36ed2`） | 改后 |
|---|---|---|
| 两条理由在账本里的名字 | `revise`、`revise.repeat` | `revise`、`revise` |
| 第二条带 `repeat_of` 指回第一条 | **是** | 否 |
| 版本 | 2 → 2 | 2 → 2 |

两条理由都是证据。第二条被记成第一条的重放，等于把新论点归档到旧论点名下：读者从账本里看到的是「同一件事说过两遍」，而不是「补了第二个理由」。卡片版本不动是对的 —— 措辞确实没改；错的是**用「状态没变」回答了「是不是同一个请求」**。

这也是 RFC 第 2 句的另一面：它允许把每次请求分别记下来，正是因为**记录的目的是分清**。把两次不同请求写成一次重放，比多写一条日志离 RFC 更远。

判据因此拆成两个问题：**版本动不动**看库存状态是否变化；**是不是重放**看请求本身（事件名 + 请求方给的细节，排除版本、改前措辞这些每次运行都不一样的记账字段）是否出现过。两条同时成立才写 `<event>.repeat`；状态没变但请求不同，就用自己的名字写一条，版本留在原处。

### 三个决定为什么算同一个经验

因为要判的是同一件事，只是换了一层：**重复请求的效果是否与单次相同，以及事后能不能分辨**。A 在网络上（要不要重发），B 在存储里（重发到了会怎样），C 在账本里（两次不同的请求会不会被当成一次）。A 的修法依据是「有证据才重试」，B 的修法依据是「日志可以多写，但版本不能假装变了」，C 的修法依据是「允许每次都记，就必须让每次都能分清」。

## 4. 修正后的判断（后来者可以直接用的形式）

> **判幂等看效果，不看次数。** 重复请求若改变了版本、计费、待办状态或对外可见的结果，它就不幂等，即使账本上只多一行。
>
> **自动重试要有证据，不能靠猜。** 只有在「语义可判定为幂等」或「可判定原请求未生效」时才重试。「连接先断了」两者都不是；「响应读不完整」是第三种情况 —— 请求可能已经生效，所以不重试，但要**如实告诉用户是传输断了**。
>
> **可以多记，不可以不可分辨。** 允许为每次请求留痕；不允许让重放与真实第二次动作在账本里长得一样。
>
> **分清要看请求，不看结果。** 两个不同请求可能把卡片带到同一个状态（同一句话、两个新理由）。判断是不是重放，要比的是请求本身；状态没变只说明版本不用动，不说明这是同一件事。
>
> **适用边界**：以上是 HTTP 语义层面的判断。它不告诉你**这个具体服务**是否幂等 —— 那要靠资源语义或版本对照（RFC 第 5 段举的版本库例子）。本仓的 `confirm` 之所以可以按效果判，是因为它的效果是「卡片变成 discussable」，这是可比较的；对一个每次调用都有新效果的端点，同样的判据会得出「不可重试」，那才是对的。

## 5. 改了什么

| 文件 | 改动 |
|---|---|
| `dojo/live.py` | 新增 `incomplete_response` 种类；比对 Content-Length，分块截断也用这一类；不保留半截正文 |
| `dojo/discuss.py` | 这一类**不自动重试**；只为「读不完整」如实说明，不再说成格式错误；这一轮记 `response_incomplete`，会话继续 |
| `dojo/storage.py` | `_write` 在效果未变时不起新版本；`_same_request` 只在请求本身重复时才写 `<event>.repeat`，否则用自己的名字写一条、版本留在原处 |
| `tests/test_repeat_safety.py` | 11 项门：A、B 各一半，C 三项（两个理由两行、同一理由仍算重放、第二个理由不重开管线） |
| `tests/test_http_interruption.py` | 两条断言从 `connect` 改为 `incomplete_response`（**这是改了已发布的断言**，理由见下） |

`tests/test_http_interruption.py` 原来把「body 被截断」钉成 `connect`。那条断言本身没错（它要保证的是不重试、不泄漏半截正文，这两点都保住了），但它把「连接失败」与「响应读不完整」压成了同一类，而这正是 A 的根因。改的是名字，不是它守的事实；两条断言的原意在新名下仍然被测。

## 5.1 我自己的第一版错在哪（全套跑出来的）

第一次改完只跑了相关文件，1025 项的全套一跑就有 37 项红。两个错都在**我这一侧**，不是旧代码的：

| 第一版 | 现象 | 修法 |
|---|---|---|
| 直接 `response.headers.get(...)` | 36 个测试红：测试双（`BytesIO`）没有 `.headers`，真实环境里也是「没有这个头」 | 没有头就是**没有这个事实**，不是「不完整」的证据；改为 `getattr` 后只在声明了长度时才比 |
| 先判完整、后判超长 | 1 个测试红：超长体是「只读到上限就停」，必然短于 Content-Length，于是被报成「响应中断」 | 超长先判。两个事实同时成立时，超长更具体、更可操作 |

第二个错值得单独说：它正是本节要治的病 —— 把一个事实报成另一个事实，让读的人去查错的地方。我在修「误诊」时又引入了一次误诊。现在这两种都有门（`tests/test_repeat_safety.py` 里的 `OversizeBodyIsNotReportedAsIncomplete`）。

## 6. 被否掉的做法

| 做法 | 为什么否 |
|---|---|
| 把 `incomplete_response` 也当 `connect` 处理（即保留自动重试，只改文案） | 仍然是猜。RFC 点名的就是这种猜，而这里已经有可检测的证据。 |
| 把 `confirm` 的重复直接拒绝，像 `add` 那样 | 会吞掉真实动作。`confirm(c1,'另一个理由')` 是有效的新决定，实测仍应写入。 |
| 重复时什么都不写 | 让重放与「用户真的又说了一遍」不可分辨，违反第 3 条。 |
| 在 `_write` 里静默 `return`（不留事件） | 同上；且排障时看不到「有人重放过」。 |
| 用时间窗口去重（例如 5 秒内相同请求算一次） | 时间不是效果。用户可能在窗口内真的改主意；这会把判断换成猜测。 |
| 只要状态没变就一律写成 `<event>.repeat`（`ce36ed2` 的做法） | 实测会把「同一句话、第二个理由」记成第一次的重放。版本对，理由丢。 |
| 第二个理由也起一个新版本，好让它不是重放 | 措辞没改，却让 `pipeline_marks` 失效、已完成的工作重新变成待办。把「分清请求」错当成了「动版本」。 |
| 在 `details` 里加一个调用方提供的 `request_id` 来判重 | 当前 CLI 每条命令都是独立进程，拿不到稳定 ID；而账本里已经存着请求的全部可比较细节，足够判同。多一个要维护的字段，不增加证据。 |

## 7. 不确定

- 只在 CPython 3.14 的 `urllib` 上实测。其它客户端/框架对截断的处理不同；`probe.py` 测的是**本仓**这条路。
- 只测了 Content-Length 与 chunked 两种框架。其它框架下「读不完整」可能表现成别的异常；`incomplete_response` 的判据是「声明的字节没到齐」，新框架要单独确认。
- 没有真实模型端点参与。`_Cut` 是本地 stub，它证明的是**本仓**在收到截断响应时的行为，不是某个厂商服务的行为。
- `_same_request` 的判据是「事件名 + 请求细节（除去 `version`/`from_statement`/`effect`/`repeat_of`）完全相同」。它默认「相同的措辞 + 相同的理由 = 同一个请求」，这与 `_strings` 的去重语义一致；它**不**比较调用方身份，所以两个不同的人碰巧写出逐字相同的理由会被算作重放。目前 CLI 没有调用方身份可比较，这是已知边界。
- 版本仍然只看状态：若将来有操作**故意**要求「内容相同也算新版本」，现有判据会把它吞掉；目前没有这种操作（`abstain` 本来就不起版本）。
- `confirm` 带会话：同一会话重复确认，实测版本不动（`confirmed_sessions` 去重后状态未变），**按重放处理**；换一个会话再来确认，版本 2 → 3，**按真实动作处理**。这一条我最初是推错的 —— 以为 `confirmed_sessions` 会追加、因而每次都会起新版本；实测否掉了。写在这里，是因为它正是本节的判据（除 `version` 外状态是否相等）在会话字段上的表现。
