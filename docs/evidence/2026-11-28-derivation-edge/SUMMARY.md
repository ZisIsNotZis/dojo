# 后来那一版和原来那条，现在有据可查了

2026-11-28。基线 `33cd298`（主管已发 master）。离线：模型是本地回环桩，回答是文件里写死的常量——
**这不是真人会话，也不是模型的判断**。全程只走标准 CLI。

## 这一片回答的问题

用主管自己的话说：一组测试都绿了，他还是在普通用法里踩到了坑；修好的是他亲手试的那条路；
另一个项目里页面没动，六条走过的路确实可以沿用。他想把「什么时候可以信以前的验收、什么时候
必须亲自再走一次」聊清楚，并看我是否留下了他真正能用的判断。

我把这套场景从头走了一遍（`.scratch/3490/walk.py`，标准 CLI + 回环桩）：

| 他后来的动作 | 结果 |
|---|---|
| 过几天只记得大意，用「测试全绿 亲手走一遍」找 | **行**：命中 6 个词，屏幕有他写的条件、反例、他自己的四条原话，以及一条可粘贴的 `discuss --card` |
| 把那条带进一场新讨论 | **行**：屏幕和发给模型的请求里都有他的原话，并说明那不是卡片的措辞 |
| 在新讨论里说「这次只有页面没动过的项目算数」，主持人改了一版，**他没有认可那版** | **断了**：库里多了一张草稿，原来那张卡一行没变，**两张卡之间没有任何关系**。再搜时屏幕把两张几乎一样的句子并列，读者无法知道哪张是从哪张来的、哪张是他后来谈过的 |

这就是这一片补的那个断点。它不是新功能，是一条**库里知道、却从来没写下来**的事实：一场讨论
开始时带着某张卡（`handout` 行、`reads` 行都在账本里），结束时写下了另一版——然后这个事实被
扔掉了。

顺带量到第二条（`.scratch/3490/probe_draft.py`）：四件答完却一句认可都没有的一场，**一张卡都
不写**，他的话只留在轨迹里。这条**不改**——「未认可不落卡」是产品规则——但它是真的，写在下面的
「仍然开着的」里。

## 改了什么

**`Store.add(..., derived_from=...)`：一条方向中立的边，和卡同一次事务写下。**

- 写进新卡自己的 `relations`，跟卡同一个版本，所以不存在「卡在、边没在」的瞬间；账本的 `add`
  行也带着 `derived_from`，读者不必比对两份状态。
- **不添来源、不动状态、不动措辞 digest**：`independence()`、`broadcast`、认可记录都不变。
- 目标先解析再存：来源卡若已被合并，边指向还在的那一张，而不是一个会随重定向链失效的旧 id。
- 写它的只有一个地方：`discuss` 在**这一场是 `--card` 带进来的、而且这是本场第一次写卡**时传这个
  id。三条写路径（当场认可的结论、会话末未认可的草稿、带着卡却没写下任何卡）分别测过。

**为什么不用 `narrows` / `generalizes`：** 程序只知道「这一版是在带着那张卡的那场里写下的」，
**不知道**是变窄还是变宽——`revise` 的历史里记着上一次这种「替读者判方向」是怎么出错的。所以
类型名是新的 `derived_from`，屏幕上的句子也照这个说：**不表示变窄或变宽**。

**读出口两头都能看见，方向各自成立。**

- 旧卡那一条：「后来有一场带着这条继续谈，写下了另一版（不是替换，也不说明变窄还是变宽；两版
  都在库里）」，下面点名 id、那一版自己的句子、它自己的认可状态，和一条 `show` 命令。
- 新卡那一条：「这条的来源：这一版是在一场带着它的讨论里写下的 X（库里记下的边，不表示变窄或
  变宽）」，并给出去看 X 的命令。
- 带进下一场讨论时，屏幕和发给模型的请求都带着同一句话。

## 复核在发布前拦住的四处（都是我这一片自己造成的）

前两处是规模，都是我先修错、再修对；后两处是屏幕说的话与记录不符。

*一、每行读一次表。* 600 张卡的库上，普通 `search` 从约 132 ms 变成约 650 ms（主管第一份复现）：
反向查找对**每一个结果行**自己跑一次 `SELECT state_json FROM candidates`，1 次变 601 次。
改成用匹配器已经读好的那份快照。

*二、每行遍历所有卡。* 表只读一次之后，反向查找仍在**每次调用时遍历所有卡片**：2400 张卡上
每行 2400 个状态，217 ms 变 513 ms，而库里一条派生关系都没有。现在每屏建一次索引
（`Store.derivation_index`），并且库里一条边都没有时连逐行查找都不进。

*（下文的三次计时数字对应这两次修复之后的状态。）*

同一份 2400 卡库上的交替 A/B（`bench.py`，各 3 轮、每轮 5 次）：

| | 基线 33cd298 | 现在 |
|---|---|---|
| 中位数 | 224.5 / 208.8 / 202.9 ms | 225.0 / 204.4 / 225.9 ms |
| 每轮最小值 | 221.2 / 202.6 / 202.3 ms | 216.6 / 198.1 / 218.9 ms |

两次变体查到的记录数一致（2400）。新加的那几件单独计时：`derivations()` 0.09 ms、
`derivation_index(2401 个状态)` 0.29 ms；整套屏幕检索 205.6 ms，给模型的那条 38.7 ms。
即这一片新加的约是原有工作量的 **0.2%**，在测得到的噪声以下。

主管的三次独立复测里，固定版比基线分别高 0%、6% 与 18%（中位 257 对 219 ms 是最差的一轮）。
**这个分歧我没有完全解释掉，也不能拿一次 A/B 抹平**：环境每次不同，而我的交替 A/B 只说明了
我这一台机器上的情况。能确定的是逐件计时：这一片新加的两件事加起来不到 0.4 ms，是整套屏幕检索
的 0.2%。若某次复测里它看起来更大，那部分时间在屏幕检索的其余 99.8% 里，不在这一片。
`bench.py` 把两种量法都印出来，让这件事可以重测，而不是被记住。
这一条也留成了常驻读数（D4/D5）与两条红臂。

**三、手打的边被说成一场讨论。** 主管的复现：一个空白库里录入并确认铁路、博物馆两张卡，两张卡各
自写成，完全没有启动讨论；手动连起来后搜铁路，屏幕却说「后来有一场带着这条继续谈，写下了另一版」，
把博物馆卡当成那次讨论的产物。

根因：我把「关系类型名」当成了「这场讨论留下的」。修法两层——

1. `link` **不再能写** `derived_from`（CLI 的选项和 `Store.link` 都拒绝）：这种边只能由程序在
   `add` 的同一次事务里写。
2. 屏幕和下一场讨论都不再靠类型名推断，而是问账本：`Store.derivation()` 读 `add` 行上的
   `derived_from`。**账本没说是程序写的，就印成「库里记着与这条有关的关系（不是一场讨论留下的，
   也不表示谁写下了谁）」**，并给出那一版的 `show` 命令。

主管自己那份 4 万字节的 `candidate.sqlite`（里面已经有一条手打边）直接拿这份树读，屏幕现在印的是
「库里记着与这条有关的关系」，不再声称有讨论。真的讨论留下的那条边仍然说「后来有一场带着这条
继续谈」。

**四、同一句话在续跑时消失。** 屏幕上「这条的来源」只在**当场的那一场**出现：续跑同一场时，
开场那屏不印。两个原因我都踩到了——`handed_derivation` 在重放时没有初始化（任何带手牌行的轨迹
续跑就 `UnboundLocalError`，13 个测试套件同时变红）；而且发放行存的 `fields` 只含七个内容字段，
不含关系，所以即使不报错，那条边也重建不出来。现在重放时从行自己的 `derived_from` 重建边，
并断言续跑的开场与当场说同一句话。

**我自己在这一片里踩到、并留成测试的：**

- `derivation()` 第一版从事件字典的顶层读 `derived_from`，而 `history()` 把它放在 `details` 里，
  于是**真的讨论留下的边反被印成「不是一场讨论留下的」**。是 `.scratch/3490/repro.py` 的 C 段
  （真讨论对照）当场抓到的，不是读代码想出来的。
- 两份「不是替换」的话术不同（新卡说「不表示变窄或变宽」，旧卡一开始只说「不是替换」），读者因此
  被留在「那是不是更窄了」的猜测里。现在两头都说不说明方向。
- 我的读数里有两项一开始写错了：一项把「被拦下的草稿仍在屏幕上」当成「在 stdout 里」；另一项把
  「两头都说」写成逐字比较两种本来就该不同的说法。

## 读数与红臂

```bash
python3 docs/evidence/2026-11-28-derivation-edge/verify.py   # 41 项读数，全部成立
python3 docs/evidence/2026-11-28-derivation-edge/redarm.py   # 11 条臂，各自红在对应检查上
python3 -B -m unittest tests.test_derivation_edge             # 16 项
python3 -B -m unittest discover -s tests -q                  # 1391 项，OK
python3 docs/evidence/2026-11-28-derivation-edge/bench.py      # 2400 卡上的交替计时与逐件耗时
```

`bench.py` 把两件事分开印：交替的中位数（跟环境和机器走）与逐件耗时（这一片到底加了多少）。

`verify.py` 的几段：A 一场讨论（卡与他的四条原话）；B 带着它谈、最后停在没人认可的另一版；
**B2 带着它谈、当场认可了新的一版**（B 走草稿路径，B2 走认可路径——两段都要，因为少一段就有一条
臂永远绿着）；C 过几天用记得的话找，两头都读得出来；D 不该有边的时候没有；D2 来源被合并后指向
还在的那张；D3 手打的边与真讨论的边在屏幕上分得开；D4 300/600 张卡时候选表都只读一次；
E 给模型的那一路没有多出屏幕键，stdout 仍是四个旧键；F 发放凭据带着这条边的凭据，续跑一致。

红臂里值得记的三条，都是**臂先绿、我才发现读数没咬住**：

- 锚点不唯一。12 个空格的缩进出现在 20 个空格的行里，替换落在了另一个调用点，臂于是绿着。
  现在每个锚点带上一行上下文，运行器要求**恰好匹配一次**。
- 一个行为有两道闸（CLI 选项 + `Store.link`），只还原一道，另一道仍然拒绝，臂绿。现在一条臂可以
  还原多处，`link` 那条同时还原两道。
- 标错了臂的名字：20 空格那个调用点是 `_save_conclusion`（当场认可），不是草稿路径。臂照样会红，
  但红在另一段的检查上。名字现在按调用点改正，两段的检查也各归其位。
- 一条臂还原的是**非法状态**而不是旧行为（把快照置空却还建索引），于是它抛 `TypeError`
  而不是红在读数上。改成同时还原两处、回到真实的旧形状。
- 还有一条臂无论怎么改都不可能红：我的「只读一次」读数在反向查找被掏空后仍为真，因为屏幕在
  缺快照时本来就拒绝读表。加上「那条边照样印出来」后它才可被证伪——**一条无法被任何臂证伪的
  读数，和没有这条读数一样。**

## 撤回 / 收窄的旧断言

- 「手打一条 `derived_from` 也算库里记下的关系」——不再成立：`link` 拒绝这个类型，`--relation`
  的选项里也没有它。这是**收窄**，理由在主管的复现里。
- `READING_ROW_KEYS` 多了 `derived_later` 和 `derivation` 两个屏幕键；给模型的每一行仍然没有它们，
  `store.retrieve()` 不加 `for_reading` 时逐字节不变（E 段读过整行）。
