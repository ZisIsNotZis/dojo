# `/认可` 只写下屏上的那一版

起点：公开提交 `3469682743c5e1fedbd23f17285e8390fdf22c93`。本轮分开记录离线回归和真实线路；前一轮仅验证了指出问题并拒绝认可，见 [SUMMARY.md](SUMMARY.md)。

## 离线：旧范围不替新范围背书

```sh
# 从候选仓库根目录运行。第二个参数必须是尚不存在的证据目录。
python3 -B docs/evidence/2026-11-28-review-before-accept/verify_review_cli.py . /tmp/dojo-review-recheck
python3 -B -m unittest tests.test_discuss_local_accept tests.test_discuss tests.test_one_card_version -q
```

脚本用本地回环桩驱动真实 CLI；它先从 stdout 解析七个字段，看到完整提示才输入 `/认可`，然后读 `show --history`、`events`、`reads` 和会话轨迹。固定的回复不出机器，认可不消耗请求。六条路径：空库；用户报告的同句撞旧卡（「先用于文档草稿」与「只用于新建的订单导出页」）；重新打开相同草稿；续跑前草稿被改；续谈旧卡后出现新版；只因归一化撞卡。实际复跑同句撞旧卡时，旧卡仍为 v3，`show --history`、`events` 和 `reads` 与认可前完全一致；只有新范围的 v1 记录了 `wording_accepted`。

已加入 `/认可`、尚未修复写入逻辑的中间版本，在离线 CLI 上有两种失败：

- 同句及同范围项目、但项目顺序不同，去重命中旧卡，实际给旧卡附上本场来源和认可，还开始四问。修复后明确提示「旧卡不等于屏上这一版」，不写认可、不发问，旧卡原封不动。
- 先原样认可交到本场的旧卡，随后显示相同句子但新范围。修复前沿用旧 ID 原地修改，旧来源就挂到了它没覆盖的范围，旧卡原有的可讨论状态也被撤掉。修复后为新范围另存，旧卡的内容、来源、状态和事件不改。

选择规则：即便内容去重判断相同，也只有**七个展示字段逐项相等**才可复用；若材料不完全相同且只因归一化撞卡，拒绝而不替人转换。只有本会话独自写下、仍等于该会话上次认可快照的卡才可原地续写。若会话草稿被另一处更改，续跑按原会话快照重新展示；旧编辑不被覆盖。四问只有在认可保存成功后才开始。

此前的四个模型认可验证器未迁移；要复跑旧证据，见[各自的公开版本](HISTORICAL-VERIFIERS.md)。

## 真实线路：读屏后才认可，不把认可当验证

只用已获准的 DeepSeek `deepseek-flash`，临时库、不读人物档案、不搜索。两场共 **3 次真实请求**：

1. 两次请求的第一场，核对时看见模型在备选里添加「退款是写操作」，而开场没有这条。操作者纠正后第二个回复缺少必填的 `answer`，未通过契约，没有选一条别的内容代写。没有认可和四问，只留下之前显示的未认可草稿。
2. 一次请求的第二场，开场给足合成场景的边界：只在新建订单导出页演示原型里，迟迟没开始时先高亮一笔普通订单；不触发导出，不改订单状态；只试一次，没有计时。屏上把它写成有条件的起手尝试，并明列速度未知，不外推到退款、批量或其他页面。实际核对后才单独输入 `/认可`。写入回执先于四问，认可和四问没有追加模型请求。

[正向证据](live-positive.json)保留屏上的原话和七字段、实际读回的七字段及认可事件。屏上、认可那轮的轨迹、`show --history` 逐字段完全相等（含范围的原有顺序）。事件记录卡号 `d-5cd9e00cc364` 和内容摘要 `b995484582606ba973140c56d87a97bdf7d0ae78863d8901774c8fad60aae873`；读回版本是 v1。这场实跑早于事件加入显式版本号，该字段由上面的离线脚本另行验证。这证明认可绑定同一份内容，不代表做法有效。四问中单独输入的「跳过。」才被标为跳过；带说明的三句作为合成会话原话附存，没有改动这七个字段。

如在已获准的线路复跑，创建独立库后执行 `python3 -m dojo --db "$DB" discuss --no-profile`。发一条上述合成原话，等完整核对段再读。不符合则不要认可。若符合，输入 `/认可`，跟随回执，用 `show ID --history` 和 `transcript` 核对。真实模型每次的提议可能不同；离线脚本用来复验版本绑定，不依赖服务返回。
