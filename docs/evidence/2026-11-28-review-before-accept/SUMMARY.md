# 在认可前核对：订单导出的一条路径

这是上一轮的历史观察。当前候选已改从公开 `34696827` 起步；[本轮证据](EXACT-VERSION.md)补上了版本冲突回归和一次真实认可。

本轮使用一个合成工作故事、普通 `discuss` 入口、临时库和获准的 DeepSeek `deepseek-flash`。每次等屏幕再输入一句，没有排入后续认可或四问的答案；不搜外网。不是业务试点，也不是模型成功率测试。候选从本地 `d81e38f` 起步；它有上一轮附答续跑修复，但本地没有索引的 `34696827` 对象，不能把两者当作同一提交。

## 最能说明改进的一段

操作者开场说「周五我们拿一笔普通订单手工点过新导出页，只打通一路」，接着说客服问了退款日期和文件交付对象。没有说成本低、也没有报客服人数。

第一场（4 次请求）在第二轮印出真实待写版本，而不是只印主持人的回答。那份提议把“成本优劣不能外推”列成边界，却另在备选和前提里写了“成本更低”“低成本分组对照”，还加上“一位客服”。操作者看到后回：「核对时我还是看见‘成本更低’和‘低成本分组对照’，这两句也都没测；‘一位’是你从‘客服在旁边’推出来的，我没报人数。」第三轮未返回合规提议；到达预算上限后，回执说这版不构成本场结论。轨迹的 `saved` 是空数组，未启动四问；库中只有系统未认可草稿。不能把“能看见和指出误归”说成“主持人已经不会误归”。

第二场（4 次请求）把开场原话也放回每次核对。原话是「客服在旁边试」和「没量人时」，待写版却有「一位客服」「未计量人数」。操作者对照原话纠正后，下一版删掉具体人数，把「工时未测，因此成本未知」放入未知，仍明确列出未试退款单和批量单。它把「上次需求会没人提」写成了「需求会没写到」，这仍是未经核对的变化；我没有认可。第四次请求没有形成可核对的新版。再次从库和轨迹读得 `saved=[]`、没有认可和四问，只有模型草稿；用收尾印出的 `show` 和 `transcript` 命令读回了成本未知与开场原字。两场共 8 次请求；**真实走通的是看见、指出和不认可，认可成功只做了离线验收。**

## 可重跑的离线对照

```sh
python3 -m unittest tests.test_discuss_local_accept tests.test_discuss tests.test_card_handoff tests.test_handoff_boundary -q
```

测试在临时库内注入固定模型回复：故意把普通收束报成 `accept`，仍不能产生认可账或启动四问；没有屏幕待核对的版本时单独输入 `/认可` 不发模型请求；核对修订版后输入 `/认可`，只保存所见的版本，再逐题提示情境、张力、代价、失效。检查 `wording_accepted` 动作及内容，不用 `status=draft` 区分认可。

若自己在已获准的线路重跑，可在独立临时库下 `python3 -m dojo --db "$DB" discuss --no-profile`，讲上面的合成故事，不先回答还没出现的提示。看真实待写段有没有把低成本写成观察，或扩大到退款单和批量单。若有，指出具体那一行；没有时再决定是否输入 `/认可`。不认可就结束，跟屏幕的 `show` 和 `transcript` 命令复核。模型提议及其边界仍可能错误；本地动作只证明你认可了那版文字，不证明事实或效用。
