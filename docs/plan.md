## 执行契约（每个里程碑统一适用）

每个里程碑完成后，向用户交付三样东西，缺一不可：

1. **测试运行报告**：开头是结论式摘要与 TL;DR，含实际运行命令、真实输出证据、未验证项与已知限制。证据绑定到 commit 或 worktree 哈希。
2. **可亲手玩的东西**：一条命令即可启动，用户在远端只需看聊天文字。
3. **重点观察清单**：明确告诉用户"这次特别该看什么"，以及什么现象说明失败。

每个里程碑在交付前必须：自查到范围内无问题，并通过**独立子代理评审**（新上下文，不用执行者上下文），评审执行者模型为 `github_copilot/gpt-6-luna`。

## M1 `discuss`：零结构负担的对齐式对话

- **目标状态**：`python3 -m dojo discuss` 启动后，用户全程只说自然语言；不出现任何卡片、表单或 y/n 提示；主持人在对话中完成镜映、锐化、溯源、设界；双方就已一条带边界的表述自然达成一致时，主持人用一句自然语言复述结论。
- **写入时机（用户已确认，取代先前的“沉默即通过”）**：写入发生在**同意发生的那一轮**，实时写入当前会话的 backing card；不等到 EOF、不等到用户按回车。“沉默”不是一种待判断的输入，而只是没有输入，**空行不写入任何结论**。因此不需要从沉默里推断同意，也不需要长期持有异议门控。
- **责任分层**：实时层只负责把当前会话达成的结论写进会话账本；树 worker 的采集、分类、连接、传播全部是**异步**的，不要求实时，也不阻塞会话。
- **交付物**：可运行的 `discuss` 模式；一次完整会话的归档记录；测试报告。
- **验收**：① 用户输入中结构化指令出现次数为 0；② 结论含 `scope`/`premises`/`alternatives`/`unknowns`；③ 用户一句反驳能推翻结论；④ 既有 27 项测试无回归；⑤ 失败路径（模型不可用、端点未配置）有清晰提示。
- **用户检查点**：亲自跑一次约 10 分钟的会话，判断"是否完全不需要管机制"。
- **依赖**：litellm 端点（`http://127.0.0.1:4000/v1`，模型 `github_copilot/gpt-6-luna`）。

## M1.5 会话轨迹与“达成即写”（用户测试前的前置）

- **目标状态**：两层同时到位。① 写入只在用户表达同意的那一轮发生，空行与 EOF 不写入；② 每场会话留下可供事后分析的**轨迹文件**，使后续 agent 能看出用户实际怎么用，而不需要用户反复重测。
- **轨迹内容（每轮一行 JSON）**：序号、时间戳、用户输入原文、主持人回答、当轮 candidate（或 null）、模型报告的 `user_stance`、当轮决定（写入/未写入）、决定的理由、累计请求数、`reasoning_effort`、`finish_reason` 和最多 65,536 字符的 `raw_response`；失败时记录 `error.kind`、HTTP 状态、结束原因与诊断文本，重试时保留逐次尝试输出。结尾一行记录本场写入的卡片 ID 与终止原因（EOF / 取消 / 上限 / 失败）。
- **存放**：默认 `<数据库目录>/sessions/<session>.jsonl`，目录 0700、文件 0600；可用 `DOJO_SESSIONS` 或命令参数覆写。开场向用户明确提示轨迹路径。
- **这改变了先前“不保存原始聊天”的 POC 选择**：是为了可分析性而作的产品层变更，由用户在对话中提出。轨迹仅存本地、不联网、不上传，并保留 `--no-trace` 关闭开关（默认开启）。
- **验收**：① 同意那一轮立即写入，空行与 EOF 不写入；② 轨迹逐轮完整、字段齐全，能被独立读取分析；③ `--no-trace` 时磁盘不产生任何轨迹文件；④ `discuss --resume <trace.jsonl>` 从原轨迹恢复历史与待定候选，并沿用 session ID 追加写入；⑤ 输出格式失败有限重试后留在会话，连续连接失败或服务端错误才结束；⑥ 既有测试无回归，新增轨迹、写入时机与续跑的回归测试。
- **用户检查点**：先自己玩一场，然后把轨迹路径告诉我，我据此分析他的实际使用方式。
- **依赖**：M1。

## M2 无声入库与会话末提炼

- **目标状态**：会话结束管线自动跑 `classify → locate → challenge`，把结论写成 draft 卡并留事件；用户只看到一句"我记下了这条，边界是……"。
- **交付物**：可玩的完整会话；提炼结果清单；测试报告。
- **验收**：① 抽检提炼结果与对话结论一致；② 单一会话来源不进入广播；③ 重复内容不产生新版本；④ 同会话重跑管线幂等无副作用；⑤ 挑战产生 `challenged` 状态且不删除旧版本。
- **用户检查点**：看提炼清单是否值得入库，还是噪音。
- **依赖**：M1。

## M3 跨用户广播回流

- **目标状态**：新会话的检索结果由主持人以"另一个陌生人在不同场景下的相容或相反主张"的转述形式带回讨论，而不是甩一个列表。
- **交付物**：可玩的三角色跨库会话；带广播 / 不带广播对照；测试报告。
- **验收**：① 两种情况有可辨识差别；② 检索报告与底层命中词一致，不夸大；③ 无命中时明确说明而非编造；④ 不把检索材料当作事实或证据。
- **用户检查点**：广播是否真的改变了讨论质量。
- **依赖**：M2。

## M4 管线配置化与上下传播

- **目标状态**：管线由 manifest 声明，pass 可插拔；新增 `generalize`（↑）与 `condition`（↓）；幂等键与环检测生效。
- **交付物**：示例 manifest；改配置即改行为的演示；测试报告。
- **验收**：① 增删 pass 只改配置、不改代码；② 不产生只复述祖先的新节点；③ pass 失败可恢复；④ 合并仍只提议不自动执行。
- **用户检查点**：配置是否直觉可用；向上归纳出的抽象是否有迁移价值。
- **依赖**：M2。

## M5 反奉承负控制与体验对等度量

- **目标状态**：一组可重复的对抗场景（用户坚持明显过窄或过宽主张），记录主持人是否让步；记录会话动作数、表单数与等待时间，与既有聊天产品对比。
- **交付物**：负控制场景集与运行输出；度量记录；测试报告。
- **验收**：① 负控制场景中主持人**不让步**且不失礼，且如实标注探针；② 表单数与结构化指令数为 0；③ 报告无过度声明（不把单样本说成效果证明）；④ 新增负控制：用户用真实文本明确反对、但模型可能误报 `user_stance` 为 `accept`，记录实际结果；未验证的一律标为风险证据，不得写成普遍可靠性证明。
- **用户检查点**：亲眼看一次"用户坚持错误、agent 不附和"的完整过程。
- **依赖**：M1、M2。

## 里程碑之后的自动推进

## M2 的工作包与依赖（门过后直接派发，此处只定拆分，不写契约）

拆分按一个字段：每个 pass 一个包，因为 pass 是 manifest 里可插拔、可单独验收的单位。依赖只有一条：先有 pass 契约，才谈三个 pass。

边表示先行，无边表示可以并行：

```
 m2a pipe-core → m2b classify
 m2a pipe-core → m2c locate
 m2a pipe-core → m2d challenge
 m2b classify  → m2e integrate
 m2c locate    → m2e integrate
 m2d challenge → m2e integrate
```

即：`m2a` 单独先行，`m2b`/`m2c`/`m2d` 三者并行，`m2e` 收口。

## 不依赖门的 M2 能力包（2026-10-21 落地，2026-10-23 补 `distill-list`；每包带命令）

门拦的是"把 M2 作为里程碑交用户过目"，不是全部 M2 代码：这些包不改 M1 行为、不改设计、不调模型，所以不等门。它们落地只意味着能力就位，**不意味着 M2 通过**——验收清单仍要等进门那一局落下（person 的，或没有 trace 时的 `m2f`）、整场跑一遍（`m2e`）才能判。

`isolation-guard` 的边界话说清楚：它拦的是 design.md 那一条「单一会话来源不进入广播」，判据是**能查到的**来源是否只有一个会话。空集不再是漏洞：没有来源组但有 `--session` 的卡，那个会话本身就是它的全部来源，因此拒收。仍放行的一类只有「来源组恰好一个，且库里查不到它是会话」——seed、模拟方法材料，以及**没带 `--session` 却把会话名写进来源组**的写入；这类卡在结果里报 `provenance_status: unidentified`、`independent: false`，缺席被点名而不是默认成通过。要不要把广播口径收紧成「两个独立组或缺席」，会让四张 seed 被拒并影响 M3 的演示材料，所以那是用户的取舍，本轮只记录（见上表后的残余风险）。

## 实验 harness（排队项：验收行与包位已写，本轮不建）

- **它是什么**：一份障碍清单 → 一条命令批量验证，每项一行可复核的结论。它不是新的产品能力，而是把「这次特别该看什么、什么现象算失败」从人脑里搬到能重复跑的地方，目前只完成过设计讨论。
- **为什么本轮不建**：20 分钟的窗口做不出一个能通过自己验收的版本。一个跑不起来的骨架比空着更差：后来的读者会把它当成已有能力引用，这比「没有」更贵。所以只有一个空位，没有占位代码。
- **验收行（这是一条契约，不是一条跑过的命令；命令尚不存在）**：建好后用 `python3 -m dojo harness run <障碍清单.md>` 判，一行一个障碍、末行汇总 `N passed / M failed`，退出码 0 当且仅当全部通过；同一清单连跑两次输出逐字相同；清单里任何一项缺「怎么算失败」就在第一行报出并整体不跑。三条都可观察，不靠自评。
- **不做什么**：不调模型（判定必须是确定性的检查，否则它是第二份模型意见，不是验证）；不改 M1/M2 行为、不改设计；不让清单变成只有作者看得懂的格式。
- **它要的包位**：一个完整包位——一份六行契约（派发时写，见 `## M2 的工作包与依赖` 末段）、一个新上下文的工作者、约 2 小时机器时间与零计量调用、一轮独立评审。它不进 20 分钟的窗口，也不等 `m2f`：没有里程碑靠它关门，它只是接在下一个有完整包位的会话上的第一件活。
